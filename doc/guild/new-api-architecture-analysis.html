一句话定位 / 01

一个多 AI 提供商统一接入网关。把 OpenAI / Claude / Gemini / AWS Bedrock / DeepSeek / 智谱 / 火山 / 腾讯等 41 个上游渠道的协议、计费、限流、配额做一层抽象，对外暴露 OpenAI 兼容接口 + 自有控制台。

架构核心矛盾：上游协议差异巨大（OpenAI Chat / Claude Messages / Gemini GenerateContent / AWS Bedrock Converse / 私有协议），网关需要在一个进程里同时跑 41 套适配器 + 计费/限流/鉴权/订阅/中间件。代码层面通过 relay/channel/<provider>/ 隔离适配器、通过 relaykit/dto 和 relaykit/relayconvert 统一内外协议转换。

关键架构观察 / 09

1. 双层"协议转换"是项目最值钱的部分

外层 relay/ 处理把 OpenAI/Anthropic 等公开协议转换为内部统一 DTO；内层 relay/channel/<provider>/ 处理内部 DTO → 上游 41 套私有协议。relaykit/dto（223 引用）和 relaykit/relayconvert 之间的边界是整个项目的"设计断层线"——改一个字段会牵动全网。

2. relay/ 是单点热点

238 个文件 / 33.5% 占比。新增渠道 = 新增一个子目录；修改计费 = 触动 `relay/common`（163 引用）。任何大改动都得兼顾"已有 41 套适配器不破"。

3. relaykit 是较新的"协议层"独立包

relaykit/dto + relaykit/types + relaykit/relayconvert + relaykit/reasonmap 共同构成对外协议抽象层。这是从早期 monolith 中抽出独立包的趋势——意味着正在做模块化拆分（参见历史 .codex-relaykit-function-architecture-analysis.md）。

4. controller 与 service 是平铺结构，不是按业务域

90 个 controller 文件、94 个 service 文件，平铺在同一个目录下，无子包。优点是简单直接，缺点是规模继续增长后领域边界会模糊。这是后续架构演进的潜在优化点。

5. Web 前端通过 embed.FS 打入二进制

//go:embed web/dist 把构建产物编进 Go 二进制，单文件部署。意味着前端构建产物 web/dist 是 new-api Docker 镜像的实际载体。

6. 41 通道 + 11 异步任务 = 项目"易扩展"特性

新增一个 AI 厂商的成本 = 新增 relay/channel/<name>/ 子目录 + 在 relay/constant 登记 + 在路由注册。这是项目作为"AI 网关聚合"的护城河。
