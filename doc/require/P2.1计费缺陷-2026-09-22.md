# StarHub 计费缺陷报告

- **版本**：v0.1.0
- **测试时间**：2026-09-22
- **测试环境**：本机 `:3001`，数据库 `starhub_test.db`
- **上游**：`https://vip.yinli.one`（OpenAI 兼容层）
- **测试方式**：真实请求，逐条与手算公式对照
- **对照需求**：`doc/require/P2计费完整性.md`

## 摘要

**单笔计费的算术是正确的，记账也是一致的；问题出在预扣和结算的边界上。**

预扣完全不按 `max_tokens` 估算（低估 6～8 倍），而结算时对差额的无条件下扣没有余额下限。两者组合，使预扣唯一的实际作用——并发透支保护——完全失效：账户余额再少，也能跑出一条费用数倍于余额的请求，并把余额扣成负数。

三个缺陷里有 2 个已在测试环境实测复现，1 个由日志反推确认。

## 环境准备

```
# 启动
STARHUB_PORT=3001 STARHUB_DB=starhub_test.db ./starhub.exe

# 登录取 session
curl -X POST http://localhost:3001/api/user/login \
  -H "Content-Type: application/json" \
  -d '{"username":"root","password":"123456"}'
```

生效的倍率配置（`GET /api/option`，2026-09-22 实测值）：

| 选项 | 值 |
| --- | --- |
| `group_ratio` | `{"default":1}` |
| `model_ratio` | `gpt-4o:2.5`、`gpt-4o-mini:0.15`、`gpt-4:10`、`claude-3-5-sonnet-20241022:3` … |
| `completion_ratio` | `gpt-4o:4`、`gpt-4o-mini:4` … |

计费公式（`relay/quota.go:21-39`）：

```
quota = (prompt_tokens × model_ratio + completion_tokens × model_ratio × completion_ratio)
        / 1e6 × 500000 × group_ratio
```

## 一、已验证正确的部分

以下均有实测对照，**无需返工**。

| 用例 | prompt / completion | 手算 | 实际记账 | 结论 |
| --- | --- | --- | --- | --- |
| gpt-4o-mini 非流式 | 19 / 200 | 61.4 → 61 | 61 | ✅ |
| gpt-4o-mini 非流式 | 20 / 249 | 76.2 → 76 | 76 | ✅ |
| gpt-4o-mini **流式** | 17 / 42 | 13.9 → 14 | 14 | ✅ |
| gpt-4o-mini 非流式 | 15 / 11 | 4.4 → 4 | 4 | ✅ |
| gpt-5（未配倍率） | 11 / 10 | 26（走 fallback） | 26 | ✅ 算术正确 |

- **流式计费正确**：上游在 `stream_options` 下返回了真实 usage 块，实际走真实 usage 结算，未退化到估算兜底。
- **三处账目一致**：`token.remain_quota`、`token.used_quota`、`logs.quota` 相互对得上；渠道 `used_quota` 同步累加正确。
- **算术实现无误**：`math.Round` 四舍五入与公式一致，逐条复算无偏差。

## 二、缺陷列表

### [严重] 1. 预扣不按 `max_tokens` 估算

**位置**：`relay/quota.go:42`

```go
estimated := EstimateTokens(ExtractPromptText(body)) + estimateReserveTokens
```

`estimateReserveTokens` 常量值仅 `100`（`relay/quota.go:19`）。预扣额度 = 只数 prompt 的 token + 固定 100，**请求里声明的 `max_tokens` 完全没有参与计算**。

**实测数据**：

| 请求 | 预扣 | 实际结算 | 低估倍数 |
| --- | --- | --- | --- |
| prompt 19，输出 200 | 9 | 61 | 6.8x |
| prompt 20，输出 249 | 9 | 76 | **8.5x** |

低估倍数随输出长度增长而放大。

**影响**：预扣是防并发透支的唯一手段。预扣额度远低于真实费用时，等于没有保护。

**对照需求**：`P2计费完整性.md` 明确要求「按 max_tokens 估算预扣」。

### [严重] 2. 结算无余额下限，余额可被扣成负数

**位置**：`relay/quota.go:102-110` 调用 `model.DecreaseUserQuotaUnconditional` / `DecreaseTokenQuotaUnconditional`（`model/user.go:83-89`）

```go
func DecreaseUserQuotaUnconditional(id int64, amount int64) error {
	return DB.Model(&User{}).Where("id = ?", id).
		Updates(map[string]any{"quota": gorm.Expr("quota - ?", amount)}).Error
}
```

该函数**没有 `quota >= amount` 条件**（对比 `DecreaseUserQuota`，`model/user.go:78` 是有条件的）。缺陷 1 造成的差额在这里被无条件下扣。

**复现步骤**：

```bash
# 1. 建一个只有 20 配额的 token
curl -X POST http://localhost:3001/api/token \
  -H "Authorization: Bearer <session>" \
  -H "Content-Type: application/json" \
  -d '{"name":"tiny-quota","remain_quota":20}'

# 2. 用该 token 发一条实际费用 61 的请求
curl -X POST http://localhost:3001/v1/chat/completions \
  -H "Authorization: Bearer <上一步返回的 key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"请写一段200字左右的介绍文字"}],"max_tokens":200}'
```

**实测结果**：

```
HTTP 200
token remain_quota: 20 → -41     # 扣穿
token used_quota:   0  → 61
```

**缓解现状（已验证）**：余额为负后再发请求会被鉴权层拦截，返回 `403 token_quota_exhausted`，**不会无限白嫖**。但单次透支已经发生，且透支规模不受账户余额约束。

**对照需求**：`P2计费完整性.md` 要求「预扣解决并发透支」。

### [中] 3. 倍率表未覆盖在用模型名，新模型静默套用 fallback

**位置**：`setting/ratio.go:16-17`（fallback 值）+ options 表的 `model_ratio` / `completion_ratio`

```go
FallbackModelRatio      = 1.0
FallbackCompletionRatio = 4.0
```

倍率表内配置的是**旧模型名**（`claude-3-5-sonnet-20241022`、`gpt-4o` 等），而实际在用的上游模型名是 `claude-sonnet-4-6`、`claude-haiku-4-5-20251001` 等新名。未命中即静默套用 fallback，**没有任何告警或日志**。

**证据（日志反推）**：`claude-haiku-4-5-20251001`，prompt 41 / completion 68，记账 quota = 157。

反推：

```
model_ratio = 1.0（fallback）、completion_ratio = 4.0（fallback）
(41×1.0 + 68×1.0×4.0) / 1e6 × 500000 = 156.5 → round = 157   ✅ 与实测一致
```

而 `claude-3-5-sonnet-20241022` 的配置倍率是 3，两者相差 3 倍以上。

**影响**：定价静默失真。fallback `1.0` 恰好比 `gpt-4o-mini`（0.15）贵 6.7 倍、比 `gpt-4o`（2.5）便宜 —— 运营改倍率表时无从得知哪些模型正走 fallback。

**建议方向**（非本次实现）：倍率未命中时应产生告警或埋点，便于运营发现在用模型是否已配置。

## 三、未被本次测试覆盖的计费路径

以下代码路径在测试中未走到，其正确性**未经实测验证**：

| 路径 | 位置 | 说明 |
| --- | --- | --- |
| 用户级配额与代币配额的一致性 | `relay/quota.go:62-79` | 代币扣减成功、用户扣减失败时会直接返回错误，不会回滚已扣的代币。两次扣减不在同一事务内（全仓无 `Transaction(`）。未构造出该失败场景。 |
| 结算差额退款 | `relay/quota.go:111-115` | `delta < 0` 时的退还路径，测试中未触发。 |
| 配额饱和换算 | `relay/quota.go:28-34` | `int64(float64)` 越界行为未验证；`common/` 下不存在 `quota_math.go`，仅 `math.Round` + `quota < 0 → 0`。 |

## 四、测试未覆盖到的风险点

- **无并发测试**：现有 `e2e_test.go` 与各单测均为串行单请求，全仓无 `-race` 用例。本报告的缺陷 1、2 在并发场景下的表现未被验证。
- **预扣原子性**：`DecreaseUserQuota`（`model/user.go:74-81`）使用 `WHERE id=? AND quota>=?` 条件更新，用户侧与代币侧的预扣本身是原子的（此项经代码核实无误，此前静态审计曾判定为"并发双花"，属误报）。

## 五、修复优先级建议

| 优先级 | 缺陷 | 位置 | 理由 |
| --- | --- | --- | --- |
| P0 | 2. 结算无余额下限 | `model/user.go:83` | 直接造成账目为负 |
| P0 | 1. 预扣不看 max_tokens | `relay/quota.go:42` | 是缺陷 2 的放大源头 |
| P1 | 3. 倍率表未覆盖新模型 | `setting/ratio.go` + options | 定价失真，影响营收 |

缺陷 1 与 2 改动集中在 `relay/quota.go` 与 `model/user.go` 两个文件，且二者需一并修复才有意义 —— 只加下限会让合理的长输出请求被误拒，只改预扣则仍存在边界穿透。
