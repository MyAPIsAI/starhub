# P2.1 billing reconciliation and model pricing follow-up

## Settlement contract

- Pre-charge continues to reserve the prompt estimate and requested completion budget.
- Settlement collects the same additional amount from the user and a limited token, bounded by the smaller available balance. Unlimited tokens do not constrain collection or change their quota counters.
- `logs.quota`, user and limited-token `used_quota`, channel `used_quota`, daily charged totals, and affiliate rebates now represent collected funds.
- `logs.unfunded_quota` records any uncollected cost. The full priced usage is `quota + unfunded_quota`. Daily summaries expose both totals.
- Shortfalls emit `[quota_shortfall]` with user, token, log ID, priced cost, collected amount, and unfunded amount after the transaction commits. A missing caller log does not prevent a shortfall record from being stored.
- Balance adjustments, counters, and the consumption log commit together. Failed transactions leave the caller's log unchanged and do not issue rebates.
- SQLite acquires a write lock before reading settlement balances to serialize concurrent settlements safely.

For example, with a user balance of 1,000 and a limited-token balance of 100, a reservation of 80 followed by a priced cost of 130 collects 100 from each. The remaining balances are 900 and 0, the usage counters and log charge are 100, and the unfunded cost is 30. A 10% affiliate rebate is 10.

Unfunded cost is an explicit gateway shortfall, not collected revenue or an automatic debt claim. This change does not retrospectively recover earlier shortfalls or reconstruct historical deductions. Pre-charge remains an estimate; upstream over-delivery, omitted output limits, or underestimated prompt usage can still produce a shortfall.

## Pricing configuration

Built-in input and completion ratios now include:

| Model | Input ratio | Completion ratio |
| --- | ---: | ---: |
| `claude-sonnet-4-6` | 3 | 5 |
| `claude-haiku-4-5` | 1 | 5 |
| `claude-haiku-4-5-20251001` | 1 | 5 |
| `gpt-5` | 1.25 | 8 |

The completion ratio is the output price divided by the input price. Baseline prices were checked on 2026-09-22 against [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing) and [OpenAI's GPT-5 pricing announcement](https://openai.com/index/introducing-gpt-5-for-developers/). These are configurable baseline rates, not a claim about a third-party upstream's contract prices.

Model and completion ratio maps override the built-in defaults. Missing built-in entries are filled when loading old options or updating options; explicit operator values, including zero, are preserved. The effective maps are persisted so the options API matches runtime pricing. Group-ratio behavior is unchanged.

Unknown token-billed models retain compatibility fallback pricing but emit `[billing_ratio_fallback]` with the model, missing option, and fallback ratio. Per-call and successful expression pricing do not warn about unused token ratios.

## Database compatibility and verification

Startup migration adds `logs.unfunded_quota` with a non-null zero default. Historical log charges remain unchanged; zero on an old row means no recorded shortfall, not proof that its original deduction was complete.

Regression coverage includes asymmetric balances, unlimited tokens, durable shortfall logs, daily totals, transaction rollback, 32 concurrent settlements, both affiliate settlement paths, known and missing model prices, preserved operator overrides, persisted legacy-option upgrades, and historical log migration.

Verification passed: `go build ./...`, `go vet ./...`, and `go test ./...`. No live upstream billing requests were sent. Concurrency was exercised by the database regression tests; the race detector was not run in this CGO-disabled environment.
