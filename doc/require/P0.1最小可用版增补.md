# P0.1 最小可用版增补：功能缺口 / 借鉴策略 / 反抄袭

> 基于读 `new-api-architecture-analysis.html` 与 `new-api-business-functions.html` 两份分析文档，对照原 `p0最小可用版.md`（转发核心）做的增补分析。
>
> 关键事实先确认：**new-api 是 AGPL-3.0**（已查 `LICENSE`），这直接决定了借鉴方式。

## 一、功能缺口分析：P0 距离“最小可用”还差什么

原 P0 文档只覆盖了**转发核心**（鉴权→选路→中转→扣费），对照业务功能清单的 5 类视角，它是一个“能跑的引擎”，但不是一个“能用的产品”。缺口分三层：

### A. 可用性缺口（没有就转不起来）

| # | 功能 | new-api 对应 | 说明 |
|---|---|---|---|
| 1 | **首启引导 Setup** | Setup 自动初始化 · DB 迁移 · 默认配置生成 · 首登 root 引导 | P0 完全缺失。没有它：部署后无管理员账号、无默认倍率，系统不可进入 |
| 2 | **注册/登录/注销闭环** | 邮箱注册 + Session 管理 | P0 只有“root 登录”一笔带过。最小集：用户名/邮箱+密码（bcrypt 哈希）、session 或 JWT、logout。邮箱验证/2FA/Passkey/OAuth 全部后置 P4 |
| 3 | **管理 API 最小集** | api-router 约 150+ 路由 | 砍到 ~15 条：channel CRUD+测试、token CRUD、user 列表/封禁/调额、option 读写、log 查询 |
| 4 | **控制台数据接口** | dashboard.go | `/api/user/self`（余额/已用量/请求数）+ 按天聚合用量（直接 `GROUP BY` logs 表，不引入 metric 体系） |
| 5 | **OpenAI 兼容错误信封** | `abortWithOpenAiMessage` | 所有转发错误必须返回 `{"error":{"message","type","code"}}` 格式——SDK 用户的第一观感。P0 隐含但未明确为验收项 |

### B. 可控性缺口（运维不失控）——“方便可控”的正题

| # | 功能 | new-api 对应 | 说明 |
|---|---|---|---|
| 6 | **options KV 配置表 + 热更新** | 9 套 setting 可热更新 | P0 把 group_ratio/model_ratio 写死在代码里。改为 options 表（key-value）+ 内存缓存 + 保存即刷新：改倍率/重试次数**不用重新编译部署**,这是“可控”的核心 |
| 7 | **渠道测试按钮** | channel_test | 管理员配完渠道点“测试”：发一条真实请求，回写 `response_time` 和状态。防止“配了渠道但 key 是错的”静默故障 |
| 8 | **基础限流** | 多档 RateLimit | 最小集两条：全局 per-IP（防扫描）+ per-user 请求频率（防单用户打爆）。模型级/令牌级限流后置 |
| 9 | **用户自查日志** | log 查询 | 用户能看到自己的调用记录（模型/时间/扣费），否则“钱扣了没有凭证”,客服压力直接到运营头上 |
| 10 | **敏感信息脱敏** | `MaskTokenKey` / channel key 清空 | GET 接口永不回显完整 key：token 打码 `sk-ab**********cd`,channel key 只留掩码。P0 表结构有 key 字段但未定义返回策略 |

### C. 明确不进最小版的（业务清单里有、但属 P1+）

支付（6 通道）、订阅、签到、邀请、2FA/Passkey/OAuth、多节点 Master/Worker、Pyroscope、i18n、异步视频任务、13 类 OpenAI 端点中的 10 类。

**结论：P0 修正版 = 原转发核心（5 表+3 中间件+1 适配器）+ 上述 A1-A5 + B6-B10,约 10 张表、~25 条管理路由、3 条转发路由。**

## 二、如何借鉴 new-api（方便且可控）

架构分析文档已把“哪里值钱”标出（依赖热度榜：common 354 / relaykit dto 223 / types 167）。借鉴的正确姿势是**按层取意，不按行取码**：

| 借鉴对象 | 借鉴方式 | 价值 |
|---|---|---|
| **数据模型**（abilities 倒排索引、5 张核心表） | 照搬概念和字段语义，重定义名 | 被 41 渠道规模验证过的路由结构，自研大概率踩一遍同样的坑 |
| **中间件链顺序**（TokenAuth → 定分组 → Distribute → 定渠道 → Relay） | 照搬顺序契约（两个 context key 的写读约定） | 分组裁决在 auth、选路在 distribute 的切分，是并发安全和重试正确性的基础 |
| **计费安全不变量**（饱和换算、乘数有界、预扣结算退款、指针+omitempty） | 当作**自己的测试验收标准**写进自己的测试 | 花钱买的教训（AGENTS.md 成文规则），纯工程知识非代码 |
| **Adaptor 接口缝** | 保留缝的位置（Convert/DoRequest/DoResponse 三段式），自己设计签名 | 渠道扩展性 = 未来接 40 厂商不改核心的保证 |
| **relaykit 独立模块** | 学“协议层独立成包、不依赖主模块”的边界 | 上层业务怎么换，协议转换层不动 |
| **embed.FS 单文件交付** | 直接采用（Go 标准库 `//go:embed`,无版权问题） | 部署便利性白拿 |
| **options 热更新模式** | 学“KV 表 + 内存原子缓存 + 保存后同步”机制 | 运维可控性的核心 |

## 三、抄袭风险与规避

### 风险定性

new-api = **AGPL-3.0**,强传染 + 第 13 条网络条款：
- 复制/修改其代码 → 你的整个作品必须以 AGPL 开源（含通过网络提供服务的情况）
- 逐行“翻译式重写”（改改变量名）仍可能被认定为衍生作品
- 其品牌/署名（QuantumNous、new-api）另受其项目政策保护，绝不能带入

### 安全边界

| 层级 | 可否使用 | 依据 |
|---|---|---|
| 架构模式、模块划分思路 | ✅ | 思想不受版权保护 |
| 数据模型概念（group/model/channel 倒排） | ✅ | 领域概念是功能需求决定的最小设计 |
| OpenAI 协议本身（13 类端点的请求/响应格式） | ✅ | 公开行业标准,谁实现都是这个样子 |
| 工程规则（不变量清单） | ✅ | 属于技术知识 |
| **具体 Go 代码、DTO 结构体、注释** | ❌ | AGPL 传染 |
| **逐文件对照重写** | ❌ | 可能被认定衍生作品 |
| **前端 UI/交互整体复刻** | ⚠️ | 界面表达有独创性；重设计布局与视觉即可 |
| 品牌、目录名照搬（如 `relay/channel`）、独特命名串 | ❌ | 显著性识别,避免任何关联 |

### 落地纪律（clean-room 流程）

```
1. 读 new-api 代码/两份分析文档 → 产出自己的「行为规格说明」（表结构字段语义、
   接口契约、不变量清单、流程图）——规格里用自己的语言
2. 合上源码，仅依据规格实现
3. 命名差异化：如 abilities → channel_routes / token → api_key / 分组语义可重定义
4. 注释、错误文案全部自写（错误文案建议直接用英文自拟，避免中文文案撞车）
5. 测试自建：不变量测试按同一规则但自己写用例
6. 保留一份「规格来源」文档，证明独立创作过程（日后争议时的证据链）
```

**合规捷径**（如果不想 rewrite）：直接 fork 并遵守 AGPL——全量开源你的修改,即可合法复用全部 41 适配器；代价是商业闭源可能性归零。两条路二选一，**最危险的是中间态：抄一部分代码又想闭源**。

## 四、两份分析文档自身的定位

它们是对 new-api 的**第三方静态分析产物**（工具链清单写明用 go list/grep 产出），作为需求输入和规格来源使用没有版权问题——但要意识到其中“模块依赖热度榜、关键架构观察”这类结论的价值：它告诉你 `common`、`relaykit/dto`、`relay/common` 是改动冲击面最大的三个包。自研时应把**这三个位置的接口稳定性设计**当作第一优先级，这比抄任何具体代码都值钱。

## 五、对原 P0 文档的修订项

| 原 P0 项 | 修订 |
|---|---|
| 默认全部 `default` 分组 | + options 表存 group_ratio,首启 seed `{"default":1}` |
| root 登录 | → 注册/登录/注销闭环 + bcrypt + session |
| 管理路由未列 | 明确 ~15 条管理 API 最小集(A3) |
| 计费 inline | 保留预扣+扣额,但倍率从 options 热读,不写死 |
| 单适配器 | 保留 1 个,但把 Adaptor 缝先定好(P3 扩展面) |
| 无运维接口 | + 渠道测试按钮、log 查询、脱敏策略(B7/B9/B10) |

修改后 P0 表数量：5 核心表(users/tokens/channels/abilities/logs) + options + (可选)sessions = ~7 表,转发 3 路由 + 管理 ~15 路由,1 适配器(OpenAI chat+models),基础限流,首启引导。
