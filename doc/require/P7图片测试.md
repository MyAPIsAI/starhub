# P7 图片测试:图片生成中继的可用性与性能实测

> 状态:已完成实测(2026-09-23)
> 结论先行:**图片生成中继功能可用**——JSON 非流式与 SSE 流式两条路径均能正确返回图片,计费准确无泄漏;网关自身开销在毫秒级(800KB 图 p50≈14ms),内存无泄漏(30 次请求后堆回到基线),单机并发吞吐 86 req/s(约 92MB/s 图片数据流)。生产环境的整体耗时由真实上游的推理时间决定,网关部分可忽略。

## 一、测试目的与范围

验证 StarHub 图片生成中继(`/v1/images/generations`,P3.1 实现)的:

1. **能否生成**:JSON 非流式 / SSE 流式两种模式,单图与多图(n=2)
2. **响应时间**:按图片尺寸、数量、流式与否分组的延迟分位数(p50/p95/p99/max)
3. **内存占用**:堆稳态、每请求分配量、峰值、GC 行为
4. **并发吞吐**:多 worker 并发下的成功率和 req/s
5. **计费正确性**:预扣-结算-退款闭环在图片路径上的表现

**不在范围内**:真实上游(OpenAI gpt-image-1 等)的推理耗时与图片质量——本测试用确定性 mock 上游隔离网关自身的开销;真实上游使用见第六节。

| 用例 | 结果 | 耗时 | 响应体 |

**结论:生成能力正常,计费精确。**

## 四、性能指标

### 4.1 响应时间(mock 上游即时应答,测得纯网关开销 + 本机 HTTP 往返)

| 场景 | 响应体 | p50 | p95 | p99 | max |
| --- | --- | --- | --- | --- | --- |
| 512x512,n=1 | 273 KB | 5.4 ms | 6.2 ms | 7.2 ms | 12.1 ms |
| 1024x1024,n=1 | 1.09 MB | 13.6 ms | 31.8 ms | 32.9 ms | 33.4 ms |
| 1536x1024,n=1 | 2.05 MB | 20.2 ms | 42.9 ms | 62.9 ms | 207.0 ms |
| 1024x1024,n=2 | 2.18 MB | 42.2 ms | 94.8 ms | 120.2 ms | 135.6 ms |
| 1024x1024,n=1,流式 | 1.10 MB | 30.6 ms | 54.0 ms | 55.5 ms | 59.8 ms |

每场景 40 次迭代(含 1 次预热)。观察:

- 延迟随载荷体积近线性增长,约 **5~10 ms/MB**(解析 + 转发 + 内存拷贝)。
- p95 与 p50 差距主要来自 GC 暂停与 SQLite 计费写盘;1536x1024 的 207ms 尾部即 GC 尖峰,属 Go 运行时正常行为。
- 流式比同体积非流式慢约 2 倍:SSE 需逐帧 flush 且逐事件解析计费,这是正确性(计费不变量)换来的固定成本。

### 4.2 SSE 端到端(模拟上游 500ms 推理延迟)

| 指标 | 值 |
| --- | --- |
| p50 | 532.6 ms |
| p95 / p99 | 557.3 ms |
| max | 587.2 ms |

即:500ms 的上游耗时上,网关叠加 33~87ms(p50 增量 32.6ms)。**真实上游秒级~十秒级的图片生成里,网关开销占比 <1%,可忽略。**

### 4.3 内存占用(30 次连续请求 × 800KB 图,Go runtime.MemStats)

| 指标 | 值 | 解读 |
| --- | --- | --- |
| HeapAlloc(前 → 后) | 1.4 MB → 1.4 MB | 请求结束后堆回到基线,**无累积泄漏** |
| 峰值 HeapAlloc | 8.2 MB | 稳态驻留极小 |
| TotalAlloc 增量 | +328.8 MB(≈11 MB/请求) | 每请求的总分配:请求体读取、b64 解析、响应转发各一份,符合"2~3 份载荷"的预期 |
| HeapInuse / Sys 增量 | -0.1 MB / +0.0 MB | 进程未向 OS 多要内存 |
| GC 次数 | 90 次(30 请求) | 约 3 次/请求,回收及时 |

**结论:内存画像健康。** 单请求生命周期内的多份拷贝(读体 → 透传 → 计费解析)是主要分配来源,若未来要优化大图场景,可将"透传 + 计费解析"合并为流式统计,减少一份拷贝。

### 4.4 并发吞吐(24 并发 × 每人 3 次,共 72 请求,1.09 MB/请求)

| 指标 | 值 |
| --- | --- |
| 成功率 | 72/72 = 100% |
| 总墙钟时间 | 835 ms |
| 吞吐 | **86.2 req/s ≈ 92 MB/s 图片数据流** |

在 24 并发下无失败、无 429(测试已抬高级联限流阈值),延迟分位数与单线程相比未见明显劣化。

## 五、综合结论

1. **能用**:JSON / SSE 两条路径、单图 / 多图、计费闭环全部正确。
2. **快**:网关开销 5~10ms/MB,p50 十几毫秒;真实场景由上游推理主导。
3. **省**:稳态堆 <10MB,无泄漏;每请求 ~11MB 瞬时分配,GC 及时回收。
4. **稳**:24 并发 100% 成功,单机 ~86 图/秒(800KB 图)——对图片网关而言,瓶颈在上游配额而非本服务。

## 六、生产使用指引(真实上游)

```bash
# 1. 管理员创建指向真实上游的渠道(type=1 OpenAI 兼容)
curl -X POST http://localhost:3000/api/channel -H "Authorization: Bearer <session>" \
  -H "Content-Type: application/json" \
  -d '{"name":"openai-image","type":1,"key":"sk-真实密钥",
       "base_url":"https://api.openai.com","models":"gpt-image-1"}'

# 2. 客户端生成(与非流式/流式同本测试用例)
curl http://localhost:3000/v1/images/generations \
  -H "Authorization: Bearer sk-starhub令牌" -H "Content-Type: application/json" \
  -d '{"model":"gpt-image-1","prompt":"a cat","n":1,"size":"1024x1024"}'
```

注意:真实计费应按官方价格配置 `model_price`(如 gpt-image-1 1024x1024 标准档约 $0.04/图),或用 `model_price_expr` 表达阶梯价。
