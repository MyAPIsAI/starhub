# P1 可靠性：让中转「不挂单」

在 P0 的 `Relay()` 单次转发外，补上生产必备的容错层。参考实现 `controller/relay.go:254-342`。

## 1.1 重试与故障转移（最优先）

| 机制 | 实现要点 |
|---|---|
| 重试主循环 | `for retryParam.GetRetry() <= common.RetryTimes`：失败后重新选渠道再转发 |
| 降级策略 | 重试时 `retry++` 使 `getChannelQuery`（`model/ability.go:101`）取下一优先级层：P0 的"最高优先级+加权随机"扩展为"优先级阶梯" |
| 不重试错误 | 4xx 客户端错误（参数错/鉴权错）直接终止，`types.ErrOptionWithSkipRetry()`；只有上游侧错误（5xx/超时/网络）才切换渠道 |
| 重试轨迹 | `addUsedChannel` 记录 `渠道1->渠道2->渠道3`，写入日志便于排障 |
| 失败退款 | `relay.go:233-242` defer `Billing.Refund()`：所有尝试失败后返还预扣费 |

**关键设计：请求体必须可重放**——P0 就要引入 `BodyStorage`（内存/磁盘缓存请求体），每次重试 `Seek(0)` 重新读。这是流式转发的隐形地基。

## 1.2 渠道健康管理

- **自动禁用**：`service/channel.go:45` `ShouldDisableChannel`（状态码规则 + 错误关键词 AC 自动机匹配）→ `DisableChannel` 置 `ChannelStatusAutoDisabled` 并通知管理员
- **自动启用**：定时探测任务成功后自动恢复（`ShouldEnableChannel`）
- **定时测活**：`controller/channel-test.go` `runChannelTestTask`——后台周期性对渠道发真实请求，测失败率决定禁用/启用，同时更新 `ResponseTime`（供路由参考）
- **手动兜底**：管理端 status 开关 + 单渠道测试按钮

## 1.3 多 Key 渠道（应对上游限频）

`model/channel.go:62` `ChannelInfo.IsMultiKey`：一个渠道存 N 个上游 key，轮询/随机模式 + 单 key 独立禁用状态（`MultiKeyStatusList`），某个 key 401/429 只禁该 key 不动整个渠道。

## P1 交付物

单渠道故障自动切换、坏渠道自动隔离、请求永不丢额度。
