## 三、尚未实现或只完成部分的内容

### 3.1 商业版资源同步与接口契约（M0、M8）

**已有基础：** 资源快照导入、目录持久化、映射、投放与发布管理。

**主要缺口：**

- 真实资源平台增量事件接收、按版本幂等应用、丢事件补拉及乱序处理的完整对接链路。
- 每 5 分钟版本对齐、差距过大时全量拉取、启动全量同步门控。
- 算法快照接收与字段校验，包括 `P`、`Q`、`score`、`state`、`trend`、`dim_scores.speed`。
- 请求级遥测批量发送、异常上报，以及仅允许资源平台调用并具有限速、防重放保护的探测接口。
- 远程与本地两种资源提供者的一致接口及行为验证。

现有 JSON 快照导入不能代表商业版真实资源同步完成。当前 `ResourceInstance` 主要包含协议、能力、上下文、地域、状态和延迟等字段，尚不足以承载 PRD 的完整算法快照。

代码依据：[资源目录与快照结构](../../model/resource_catalog.go)、[路由注册](../../internal/router/router.go)。

### 3.2 文本智能路由执行（M2）

**已有基础：** 亲和、优先级与权重选路、故障切换、智能入口的部分选择与会话约束。

**主要缺口：**

- 资源价格折数 `P`、质量等级 `Q` 与服务分组档位 `G` 的过滤。
- 消费资源平台评分并排序，而非使用现有优先级加权逻辑代替评分路由。
- 前三名按 **7∶2.5∶0.5** 分流、第四名仅参与失败顺延。
- 本机熔断、半开探测、EWMA 降权与相应状态上报。
- 快照超过 3 分钟后的兜底模式，以及新快照到达后的恢复。
- 按 PRD 完整验收重试资源数量、总时间预算及有状态请求处理边界。

当前选路核心仍是按优先级分层、层内按权重选择，不能视为《算法升级版》执行链路已经完成。

代码依据：[当前渠道选择逻辑](../../model/ability.go)、[亲和状态](../../model/affinity.go)、[请求与重试流程](../../controller/relay.go)。

### 3.3 Key 管控（M3）

**已有基础：** 服务分组、模型授权、额度限制、有效期、IP 白名单、启停、重生成及本人密码验证。

**主要缺口：**

- 每日／每月额度重置、按地区时区日切，以及周期历史。
- 分开记录本周期用量、额度上限和累计总用量，并提供相应详情。
- 与模型授权范围独立保存的智能入口开关、候选模型配置。
- 密码重新验证后重复取回完整 Key，以及相应查看审计。

前端适配器明确将后端 Key 额度周期设为 `never`；当前后端没有周期重置概念。智能入口权限由模型授权推导，尚不是 PRD 的独立属性。完整 Key 主要在创建／重生成时返回，密码验证接口只返回验证结果，不返回可重复读取的凭证。

代码依据：[Key 数据模型](../../model/token.go)、[Key 适配器](../../web/src/lib/api/key-adapter.ts)、[密码验证接口](../../controller/token_password.go)、[前端 Key 接口契约](../../web/src/lib/api/tokens.ts)。

### 3.4 统一计费精度与可复算记录（M4）

**已有基础：** 表达式计价、分时价格、独立 Token 价格、受理时价格快照，以及预扣、失败退款、实际用量结算。

**主要缺口：**

- 调用结算与余额统一达到 PRD 的纳美元记账精度。
- 保存完整计价输入、价格版本及舍入前精确费用，支持复算与审计。
- 按 PRD 核对所有计价模式、条件单位价与叠加规则的完整覆盖。
- 地区时区下的受理日归属、跨日流式结算和后续补对。

当前 `1 USD = 500000 quota`，因此 **1 quota = 2000 纳美元**。部分价格输入虽已使用精确计算，最终调用仍转换为整数 quota；钱包使用纳美元不等于整条调用账务链已经达到纳美元精度。

代码依据：[额度换算常量](../../common/config.go)、[最终计价与舍入](../../relay/pricing.go)、[独立 Token 价格计算](../../relay/token_rates.go)。

### 3.5 账本、钱包与每日对账（M4）

**已有基础：** Wallet、LedgerEntry、充值订单，以及 quota 预扣与结算事务。

**主要缺口：**

- 充值资金、账户余额、调用扣费和账本流水形成统一闭环。
- 所有余额变动均有对应的可追溯流水，并可由流水重建余额。
- 地区时区 **02:00 自动对账**，包括余额、扣费、充值和 Key 用量。
- 差异记录、告警、未完成请求后续补对及修复流程。

API 消费扣的是用户和 Key 的 quota；充值增加的是 Wallet。消费结算没有同步形成对应 Wallet 流水，钱包接口明确返回 `api_quota_conversion_available: false`。不能将现有充值流水或结算一致性测试视为每日财务对账已经完成。

代码依据：[钱包接口](../../controller/billing.go)、[消费结算](../../model/quota.go)、[充值入账](../../model/billing.go)。

### 3.6 真实充值、加款与退款（M4）

**已有基础：** 订单状态机、模拟支付结果、模拟入账及并发幂等保护；后台可调整 quota。

**主要缺口：**

- 真实支付渠道和服务端可信回调，包括验签、订单匹配及幂等入账。
- 可信资金与 API 调用额度的衔接。
- 拒付、退款、晚到回调等真实支付生命周期处理。
- 后台加款／扣回进入统一账本，而不只是直接修改 quota。

当前订单创建和成功入账明确标记为 `simulation`；前端支付结果仍由手动模拟产生。真实支付应使用独立的认证回调流程，不能直接把现有用户模拟 `resolve` 当作支付回调。

最新版 PRD 已撤回「大额双人复核」，首发后台加款允许单人执行并留审计痕，因此双人复核不应列为首发缺口。

代码依据：[充值模型与模拟资金来源](../../model/billing.go)、[充值处理接口](../../controller/billing.go)、[充值交互](../../web/src/features/recharge-flow.tsx)、[后台 quota 调整](../../controller/user.go)。

### 3.7 账户与认证（M5）

**已有基础：** 用户名密码注册登录、密码与资料邮箱修改、会话管理、安全事件、账号注销。

**主要缺口：**

- 手机号注册与绑定、短信验证码校验、短信登录和找回密码。
- 真实短信及验证邮件通道。
- 登录失败锁定、人机验证等 PRD 规定的认证防刷能力。

当前登录与注册界面已明确说明短信、验证邮件和密码找回不可用。资料邮箱修改不代表邮箱验证或邮件认证已完成。

代码依据：[注册与登录](../../controller/user.go)、[认证界面](../../web/src/pages/auth/auth-dialog.tsx)、[账户安全界面](../../web/src/features/account-security.tsx)。

### 3.8 管理后台安全与凭证保护（M7、M10）

## 五、看板状态及文档口径需要校准的内容

1. **接口契约：** 看板关联任务已全部登记完成，但本地代码未找到商业版真实同步、遥测、探测等完整实现，不能直接沿用完成结论。
2. **Key 周期：** 看板存在已完成的周期重置任务，而当前适配器明确说明后端没有周期概念。
3. **账户认证：** 看板关联任务已全部登记完成，但最新版需求要求的短信认证与找回密码仍不可用。
4. **地区档案：** 看板关联任务已全部登记完成，但现有资源地域模型不能替代完整地区档案。
5. **凭证加密：** 看板有已完成的加密与轮换任务，当前 Key 存储尚未体现相应实现。
6. **资源投放：** 当前代码已有大量后端实现，不能沿用早期文档中「仅 localStorage 演示」的判断。
7. **视频任务：** 需求保留且代码已有实现，但有效关联任务为空，不能以任务数为零推断功能已完成或无需工作量。
8. **重复任务：** 同一功能同时存在汇总任务与细项，重新排期前应先去重，再核实实现与验收剩余量。

仓库中的 [未实现能力登记](../../testdata/blocked-capabilities.json) 也存在历史信息，尤其资源投放条目已落后于当前代码，不能单独作为最终判断依据。

## 十一、resource 平台集成契约分析（2026-11-12）

上级目录 `D:\Workspace\resource`（模块名 `smart-routing-resource-platform`）是真实的商业版资源平台。本章记录其与 StarHub 的集成契约，并据此更新 A 组、B 组任务的判断。local 模式（T55）确认搁置，由 resource 平台接管评分和快照发布。

### 11.1 平台定位

resource 平台是**控制面**：评分、策略、保护状态、快照发布。
StarHub（Talen/new-api）是**数据面**：路由流量、收集指标、发送事件、执行探测、应用快照。

两者通过 HTTP 双向通信，不校验签名，依赖内部网络信任（Docker 共享网络或 loopback）。

### 11.2 集成方向总览

| 方向 | 说明 |
|---|---|
| resource → gateway（拉取） | 目录（`/api/channel/models/details`、增量 `/api/channel/models/changes`、版本 `/api/channel/catalog/version`）、指标（`/api/metric/redis|mysql|model/redis|model/mysql`）、连通测试（`/api/channel/test/:id`）、策略同步状态（`/api/metric/routing/policy-status`） |
| resource → gateway（推送） | 快照（`POST /api/metric/runtime/summary`，包含完整 `route_snapshot` + 运行时指标摘要） |
| gateway → resource（推送） | 目录变更通知（`POST /internal/catalog/events`）、保护事件（`POST /internal/routing/protection-events`）、硬失败流（`POST /internal/routing/hard-failure-events`）、探测结果（`POST /internal/routing/observations/v2/results`） |
| gateway → resource（拉取） | 探测观察任务（`POST /internal/routing/observations/v2/claim`） |

### 11.3 快照数据结构

resource 平台发布的 `RouteSnapshotItem` 已包含 A 组 T05 和 B 组所需的全部字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `resource_id` | string | 格式 `<channel_id>:<model_id>:t<price_tier>` |
| `state` | string | `hot`/`cold`/`cold_new`/`cold_silent`/`degraded`/`disabled`/`bad` |
| `trend` | string | `stable`/`degraded`/`degrading` |
| `quality_level` | string | `S0`/`S1`/`S2`/`UN`/`IN` |
| `score` | float64 | 综合排序分 |
| `dim_scores` | object | `success_rate`/`cost`/`speed`/`health`/`stability`（均为 float64） |
| `pricing` | object | 分组倍率定价（schema v4，`cost_basis=group_ratio`） |
| `protection` | object | 目录排除、模式、恢复 epoch |
| `score_evidence` | object | 五维证据、生命周期（`lifecycle.admission`: `normal`/`cold`/`fallback_only`/`limited`/`blocked`） |

快照通过 `POST /api/metric/runtime/summary` 推送到 gateway，gateway 必须返回 `protection_receipt`（`applied=true, shared=true`，匹配 `snapshot_version` + `checksum`），否则 resource 标记投递失败。

### 11.4 StarHub 侧需实现的端点（resource 调用 gateway）

| 端点 | 方法 | 用途 |
|---|---|---|
| `POST /api/metric/runtime/summary` | POST | 接收快照 + 返回保护收据 |
| `GET /api/metric/redis` | GET | Redis 分钟桶 + EWMA |
| `GET /api/metric/mysql` | GET | 15 分钟指标窗口 |
| `GET /api/metric/model/redis` | GET | 按模型 Redis 指标 |
| `GET /api/metric/model/mysql` | GET | 按模型 15 分钟指标 |
| `GET /api/metric/routing/policy-status` | GET | 实例策略同步状态 |
| `GET /api/channel/models/details` | GET | 全量渠道模型目录 |
| `GET /api/channel/models/changes?since_revision=N` | GET | 增量目录差异（409 → 全量回退） |
| `GET /api/channel/catalog/version` | GET | 当前目录版本 + 更新时间 |
| `GET /api/channel/test/:id?model=<model>` | GET | 渠道连通测试 |

以上端点均需 `Authorization: Bearer <METRIC_AUTHORIZATION>`。StarHub 当前使用独立服务凭证校验，不复用普通 admin/root 会话或客户 API Key；轮换由 root 管理端点执行。

### 11.5 StarHub 侧需实现的发送端（gateway 调用 resource）

| 目标端点 | 触发条件 | 请求体 |
|---|---|---|
| `POST /internal/catalog/events` | 渠道/模型变更时 | `{event, revision, changed_channels[], changed_models[], changed_count}` |
| `POST /internal/routing/protection-events` | 保护事件发生时 | `routingprotection.Event`，需 `X-Protection-Node` 头 |
| `POST /internal/routing/hard-failure-events` | 硬失败流 | `[]routingprotection.Event`（批量，最多 64 条） |
| `POST /internal/routing/observations/v2/claim` | worker 轮询 | `ObservationClaim`，需 `probe_id` |
| `POST /internal/routing/observations/v2/results` | 探测完成后 | `ObservationResult`，含 TTFT/成功率 |

### 11.6 配置项

| 环境变量 | 说明 |
|---|---|
| `NODE_NAME` | 每个 gateway 节点的持久唯一标识（作为 `X-Protection-Node` 头和 body 中的 `instance_id`） |
| `RESOURCE_CATALOG_NOTIFY_URL` | resource 平台 base URL（如 `http://resource-backend:3001`），启用保护投递和观察 worker |
| `RESOURCE_CATALOG_NOTIFY_ENABLED` | 仅控制目录通知（不影响保护/观察） |
| `METRIC_AUTHORIZATION` | StarHub 初始独立服务凭证，填原始 token；resource 调用 gateway 时发送完整 Bearer 请求头。已轮换后以数据库中的凭证摘要为准 |
| `ROUTING_OBSERVATION_V2_ENABLED` | 默认 `1`（开启）；混合版本滚动升级时设为 `0` |

### 11.7 部署顺序

始终**先升级 gateway 接收端，再升级 resource 发布端**。旧接收端无法接收新快照 schema（如 schema 4 分组倍率定价）。resource README 多处强调此顺序。

### 12.2 T06：新版契约已有实现依据，但需校准验收口径

StarHub 已有尝试级采集、四类指标拉取接口及有界分钟桶，但现有统计主要保存在进程内存中，尚未补齐原请求级能力／亲和字段和新版完整分钟生产覆盖证据。

相邻 resource 项目已定义 `ProductionManifest`、`confirmed-production-attempts-v2` 和 `__production_coverage_v2__`，并校验分钟连续性、资源代际、清单与逐资源计数的一致性。因此，补齐这部分证据已有具体接收契约可依，不需要先改为分布式部署。

后续实现应覆盖以下边界：

- 明确每次真实上游尝试的能力、亲和及资源身份来源，避免只给聚合结果增加字段而丢失原始语义。
- 区分“确认无请求的零值分钟”和“数据缺失／不完整的分钟”；不能因缓存溢出或进程重启而把缺失数据声明为完整零值。
- 明确分钟封账、迟到结果、资源代际切换和重复拉取的规则，并验证 resource 实际可以接收、保存和用于评分。
- 对齐原完成条件中的“逐请求异步批量发送”与当前商业集成的“分钟聚合拉取”。补齐拉取契约不自动等于完成原逐请求推送要求，需明确最终验收口径。

代码依据：[StarHub 指标字段及分钟采集](../../metric/resource_platform.go)、[请求与尝试元数据](../../metric/metric.go)、[resource 完整分钟清单](../../../resource/pkg/routingscore/production_manifest.go)、[resource 同步校验](../../../resource/metric/production_sync.go)。

### 12.3 T07：EWMA 上报需要接收端同步扩展

StarHub 的本机路由状态已记录 `ewma_latency` 和 `ewma_recovered`。resource 的保护事件接收端对普通事件原因目前仅接受 `half_open_failures` 和 `recovery_success`，硬失败流走独立校验路径；不能直接发送新增 EWMA 原因并假定接收端会处理。

后续需两侧共同明确 EWMA 事件字段、降级／恢复语义、资源代际及状态版本、幂等身份、去重、重试、回执和可查询结果。还应区分“网关本机延迟保护”与“资源平台评分／状态决策”，避免把本机 EWMA 异常伪装成硬失败事件而改变其业务含义。升级顺序应保证接收端先兼容新增事件，再启用发送。

代码依据：[StarHub 本机 EWMA 状态](../../model/local_routing.go)、[StarHub 事件投递](../../service/resource_platform.go)、[resource 保护事件接收](../../../resource/service/routing_protection.go)。

### 12.4 T26：前置条件是金额方案，不是更换存储架构

当前 `1 USD = 500000 quota`，即 `1 quota = 2000 纳美元`；钱包使用纳美元，但调用结算最终仍落为整数 quota。`ExactFeeMicroUSD` 只能作为现有费用记录的一部分，不能替代端到端的纳美元核算。

从现有代码判断，单实例 SQLite 及事务机制本身不阻止统一金额精度。前文“等待 D01”应进一步细化为需要落实金额刻度、舍入和迁移等方案，不能笼统理解为必须等待 Redis/MySQL 或多实例架构。这是本次技术可行性判断，不表示账务方案已经确定。

实施前至少应明确：统一存储金额单位、价格及倍率计算方式、舍入发生位置、最小收费规则、溢出边界、API 的数值／字符串兼容方式。迁移范围需包含账户和 Key 余额、已用计数、周期上限及历史、预扣收据、待结算意图和异步任务。旧 quota 可按原换算关系转换，但必须保留历史单位或版本并核对金额；不能只修改 `QuotaPerUSD` 常量后直接解释旧数据。

代码依据：[quota 换算常量](../../common/config.go)、[计价及精确费用记录](../../relay/pricing.go)、[舍入与范围保护](../../common/quota_math.go)、[周期及预扣记录](../../model/token_period.go)。

### 12.5 T28：先统一账本单位和资金真源，再接可信资金

当前 API 调用扣减用户／Key 的 quota，充值增加 Wallet；钱包接口明确返回 `api_quota_conversion_available: false`。已有消费日志、充值流水和后台调整流水不能直接视为可重建余额的统一资金账本。

本次核对还确认一个需要处理的具体问题：`LedgerEntry.Amount`、`BalanceAfter` 定义为纳美元，但 `AdjustUserQuota` 写入同一表时使用 quota 数值及 quota 余额，缺少独立单位标识。两种数值刻度相差 2000 倍，不能直接求和，也不能在迁移时统一把全部历史流水乘以同一系数。

后续应与 T26 串行落实以下工作：

- 明确 Wallet 与调用可用余额的关系，确定资金真源、预扣占用和余额重建规则，避免两套余额相互覆盖。
- 将消费、退款、调整及可信入账纳入一致的事务和业务幂等体系；将账本变动与日志、预扣／结算收据关联，支持从可信期初余额及后续流水核对余额。
- 按历史业务来源识别旧流水的单位和资金性质，保留迁移映射及核对证据；不能把历史未验证资金自动升级为可信支付资金。
- 可以先建设有审计的后台加款路径或预留可信入账接口；是否作为可消费资金来源，需要在资金规则中明确。现有模拟充值继续隔离，不得通过手动选择成功结果产生可消费资金。
- 真实支付渠道、验签回调及退款／拒付仍由 T31–T33 跟踪。它们的搁置不必阻塞统一账本核心，但未接入前不能宣称真实支付资金链路已验收完成。

代码依据：[钱包、流水及资金来源定义](../../model/billing.go)、[后台 quota 调整写流水](../../model/quota_adjustment.go)、[调用结算](../../model/quota.go)、[钱包能力声明](../../controller/billing.go)。

#### 风险 1：环境变量文档缺失（中风险）

| `STARHUB_ADMIN_IP_WHITELIST` | 后台 IP 白名单（T46） | `main.go:60` |
| `STARHUB_CRYPTO_SECRET` | AES-256 加密密钥（T43） | `common/crypto_secret.go:34` |
| `STARHUB_ROOT_PASSWORD` | Root 初始密码 | `config/startup.go:65` |
| `STARHUB_BACKUP_DIR` | 备份目录（T59） | `controller/backup.go:20` |

#### 风险 2：`STARHUB_CRYPTO_SECRET` 未设置时的重启行为（中风险）

`common/crypto_secret.go:27-50` 在环境变量未设置时生成随机密钥：

- 首次启动：正常工作，Token.Key 和 Channel.Key 被加密
- 重启后：新随机密钥无法解密旧数据，所有已存储的 API Key 和渠道凭证变为不可解密

**影响：** 生产部署如果不设置 `STARHUB_CRYPTO_SECRET`，重启后所有 API Key 失效。

**建议：** 在 `main.go` 启动时检测到生产模式且未设置 `STARHUB_CRYPTO_SECRET` 时发出 WARNING 日志，或在 `model.MigrateCredentialStorage` 中拒绝使用随机密钥迁移已有加密数据。

#### 风险 3：resource 平台集成未经真实联调（中风险）

A 组（T01–T10）和 B 组（T11–T18）的代码已实现（`1465c21`–`227a213`），但仅通过本地回归测试验证。V01 验收状态为「部分验收：本地回归已执行，真实平台联调尚未执行」。

**影响：** 快照接收（`POST /api/metric/runtime/summary`）、保护事件投递（`/internal/routing/protection-events`）、观察 worker（`/internal/routing/observations/v2/*`）在真实网络环境下可能存在协议不匹配、超时或 TLS 配置问题。

**建议：** 在真实 resource 平台环境中执行端到端联调，覆盖快照推送→接收→应用→保护收据回传全链路。

#### 风险 4：SQLite 单写者瓶颈（架构风险）

当前 SQLite + WAL + `busy_timeout(10s)` 在高并发写入场景下可能超时。`model/quota.go` 的所有 quota 变更（预扣 `ReserveQuota`、结算 `ApplyQuotaSettlement`、退款 `RefundQuota`）都是写事务。在 1500 QPS 目标下，SQLite 的单写者序列化会成为瓶颈。

**影响：** 高并发场景下 `SQLITE_BUSY` 超时（10 秒后返回错误）。当前 `busy_timeout` 为 10 秒，可缓解短时竞争，但持续高写入会导致用户可感知的延迟和失败。

**缓解：** P36（`doc/require/P36.Mysql&PostgreSql支持扩展.md`）已分析 MySQL/PostgreSQL 扩展路径，行级锁可替代表级锁。切换数据库的代码改动量约 300 行，但在 D01 决策前保持 SQLite 默认。

#### 风险 5：测试偶发不稳定（低风险）

`TestTokenPasswordVerificationIsOwnerBoundReadOnlyAndCookieFree` 在全包测试中偶发失败，单独运行通过。原因是测试间共享全局 `model.DB` 状态污染——某个前置测试修改了全局数据库状态后未完全回滚。

**影响：** 不影响生产，但 CI 可能偶发误报，需要重跑。

**建议：** 为该测试添加独立的 `newTestDB(t)` 隔离，或确保前置测试清理全局状态。

#### 风险 6：备份仅支持 SQLite（低风险）

`controller/backup.go:29` 使用 SQLite 专有的 `VACUUM INTO`。切换到 MySQL/PostgreSQL 后备份端点返回错误。

**影响：** 仅在切换数据库后影响。当前 SQLite 部署不受影响。

**建议：** P36 已分析按驱动分支处理。当前可保持不变。

#### 风险 7：会话存储为进程内存（已知限制）

`middleware/session.go` 使用 `map[string]*sessionData` + `sync.RWMutex`。重启丢失所有会话，不支持多实例。这是 T58 的已知限制，依赖 D01 决策。

**影响：** 进程重启后所有用户需重新登录；多实例部署时会话不共享。

#### 风险 8：部分索引和 date()/strftime() 不跨库（已知限制）

| SQLite 专有语法 | 代码位置 | 跨库影响 |
|---|---|---|

| `strftime('%Y-%m-%d', ts, 'unixepoch')` | `model/service_quality.go:155,224` | 同上 |

P36 已分析方言函数替换方案。当前 SQLite 部署不受影响。

### 16.4 已确认的配置与性能风险

| 风险 | 触发条件与实际影响 | 上线处理原则 |
|---|---|---|
| 密钥跨重启不稳定 | 未设置 `STARHUB_CRYPTO_SECRET` 时生成随机密钥。已有加密凭证或客户 Key 哈希后，重启可能解密失败或因迁移校验失败而无法启动。显式凭证密钥环也不能替代客户 Key 哈希所需的稳定 HMAC 密钥 | 使用持久、保密的配置并保留恢复所需旧版本；随数据库备份保护密钥。不能以第一次启动成功证明重启安全。见 [密钥说明](../../CREDENTIAL_STORAGE.md) |
| 默认管理员口令与网络暴露 | 未设置初始密码时仍使用 `root`／`123456`；默认绑定地址为空，会监听所有网卡。首次改密和 2FA 门禁已有实现，但不能替代初始化阶段的访问保护 | 设置安全初始密码，限制初始化和后台访问，正确配置 TLS、Cookie 及可信代理。依据：[启动入口](../../main.go)、[默认配置](../../common/config.go) |

| 每分钟重复核对全部历史 | 调度每分钟枚举用户与历史业务日；每个日期再次读取该用户的消费流水并执行全账本、Key／周期核验，部分处理持有用户写锁。历史和用户数量增长后会放大数据库负载与账务等待 | 优先考虑已变化业务日、处理水位、有界分页及独立的周期全量核验，同时保留迟到补对和重启恢复语义；优化前先固定数据量测量。依据：[调度](../../service/reconciliation.go)、[对账实现](../../model/daily_reconciliation.go) |
| 示例配置滞后 | `config.example.yml` 仍注明仅支持 SQLite、网络库未开放，与当前代码不一致 | 校准部署说明及驱动前提，避免仅依照旧示例判断功能状态。依据：[示例配置](../../config.example.yml) |
| 数据库部署与容量前提 | MySQL 启动要求 `max_allowed_packet` 至少 65 MiB；大 Payload、网络延迟、连接竞争、SQLite 单写者和长期保留均会影响实际吞吐及尾延迟 | 按部署版本、负载和保留周期验收，不将本地功能测试或短基准换算为生产 QPS。依据：[数据库连接](../../model/database_connection.go)、[P37](P37.数据埋点监控分析.md) |
