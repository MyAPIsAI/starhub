### 1.2 主要结论

当前代码已具备较完整的网关和控制台基础，但商业版资源对接、算法路由、统一账务、真实支付、短信认证及上线保障仍有明显缺口，不能据此认定「自研 API 平台 1.0」已经达到完整交付标准。

看板状态与代码实现并不同步：部分仍处于开发中的任务已有大量实现；部分已登记完成的任务，在本地代码中仍未找到满足最新版 PRD 的对应实现。应按「任务状态、代码覆盖、验收结果」分别判断。

## 三、尚未实现或只完成部分的内容

### 3.1 商业版资源同步与接口契约（M0、M8）

**已有基础：** 资源快照导入、目录持久化、映射、投放与发布管理。

**主要缺口：**

- 真实资源平台增量事件接收、按版本幂等应用、丢事件补拉及乱序处理的完整对接链路。
- 每 5 分钟版本对齐、差距过大时全量拉取、启动全量同步门控。
- 算法快照接收与字段校验，包括 `P`、`Q`、`score`、`state`、`trend`、`dim_scores.speed`。
- 请求级遥测批量发送、异常上报，以及仅允许资源平台调用并具有限速、防重放保护的探测接口。
- 远程与本地两种资源提供者的一致接口及行为验证。

现有 JSON 快照导入不能代表商业版真实资源同步完成。当前 `ResourceInstance` 主要包含协议、能力、上下文、地域、状态和延迟等字段，尚不足以承载 PRD 的完整算法快照。

代码依据：[资源目录与快照结构](../../model/resource_catalog.go)、[路由注册](../../internal/router/router.go)。

### 3.2 文本智能路由执行（M2）

**已有基础：** 亲和、优先级与权重选路、故障切换、智能入口的部分选择与会话约束。

**主要缺口：**

- 资源价格折数 `P`、质量等级 `Q` 与服务分组档位 `G` 的过滤。
- 消费资源平台评分并排序，而非使用现有优先级加权逻辑代替评分路由。
- 前三名按 **7∶2.5∶0.5** 分流、第四名仅参与失败顺延。
- 本机熔断、半开探测、EWMA 降权与相应状态上报。
- 快照超过 3 分钟后的兜底模式，以及新快照到达后的恢复。
- 按 PRD 完整验收重试资源数量、总时间预算及有状态请求处理边界。

当前选路核心仍是按优先级分层、层内按权重选择，不能视为《算法升级版》执行链路已经完成。

代码依据：[当前渠道选择逻辑](../../model/ability.go)、[亲和状态](../../model/affinity.go)、[请求与重试流程](../../controller/relay.go)。

### 3.3 Key 管控（M3）

**已有基础：** 服务分组、模型授权、额度限制、有效期、IP 白名单、启停、重生成及本人密码验证。

**主要缺口：**

- 每日／每月额度重置、按地区时区日切，以及周期历史。
- 分开记录本周期用量、额度上限和累计总用量，并提供相应详情。
- 与模型授权范围独立保存的智能入口开关、候选模型配置。
- 密码重新验证后重复取回完整 Key，以及相应查看审计。

前端适配器明确将后端 Key 额度周期设为 `never`；当前后端没有周期重置概念。智能入口权限由模型授权推导，尚不是 PRD 的独立属性。完整 Key 主要在创建／重生成时返回，密码验证接口只返回验证结果，不返回可重复读取的凭证。

代码依据：[Key 数据模型](../../model/token.go)、[Key 适配器](../../web/src/lib/api/key-adapter.ts)、[密码验证接口](../../controller/token_password.go)、[前端 Key 接口契约](../../web/src/lib/api/tokens.ts)。

### 3.4 统一计费精度与可复算记录（M4）

**已有基础：** 表达式计价、分时价格、独立 Token 价格、受理时价格快照，以及预扣、失败退款、实际用量结算。

**主要缺口：**

- 调用结算与余额统一达到 PRD 的纳美元记账精度。
- 保存完整计价输入、价格版本及舍入前精确费用，支持复算与审计。
- 按 PRD 核对所有计价模式、条件单位价与叠加规则的完整覆盖。
- 地区时区下的受理日归属、跨日流式结算和后续补对。

当前 `1 USD = 500000 quota`，因此 **1 quota = 2000 纳美元**。部分价格输入虽已使用精确计算，最终调用仍转换为整数 quota；钱包使用纳美元不等于整条调用账务链已经达到纳美元精度。

代码依据：[额度换算常量](../../common/config.go)、[最终计价与舍入](../../relay/pricing.go)、[独立 Token 价格计算](../../relay/token_rates.go)。

### 3.5 账本、钱包与每日对账（M4）

**已有基础：** Wallet、LedgerEntry、充值订单，以及 quota 预扣与结算事务。

**主要缺口：**

- 充值资金、账户余额、调用扣费和账本流水形成统一闭环。
- 所有余额变动均有对应的可追溯流水，并可由流水重建余额。
- 地区时区 **02:00 自动对账**，包括余额、扣费、充值和 Key 用量。
- 差异记录、告警、未完成请求后续补对及修复流程。

API 消费扣的是用户和 Key 的 quota；充值增加的是 Wallet。消费结算没有同步形成对应 Wallet 流水，钱包接口明确返回 `api_quota_conversion_available: false`。不能将现有充值流水或结算一致性测试视为每日财务对账已经完成。

代码依据：[钱包接口](../../controller/billing.go)、[消费结算](../../model/quota.go)、[充值入账](../../model/billing.go)。

### 3.6 真实充值、加款与退款（M4）

**已有基础：** 订单状态机、模拟支付结果、模拟入账及并发幂等保护；后台可调整 quota。

**主要缺口：**

- 真实支付渠道和服务端可信回调，包括验签、订单匹配及幂等入账。
- 可信资金与 API 调用额度的衔接。
- 拒付、退款、晚到回调等真实支付生命周期处理。
- 后台加款／扣回进入统一账本，而不只是直接修改 quota。

当前订单创建和成功入账明确标记为 `simulation`；前端支付结果仍由手动模拟产生。真实支付应使用独立的认证回调流程，不能直接把现有用户模拟 `resolve` 当作支付回调。

最新版 PRD 已撤回「大额双人复核」，首发后台加款允许单人执行并留审计痕，因此双人复核不应列为首发缺口。

代码依据：[充值模型与模拟资金来源](../../model/billing.go)、[充值处理接口](../../controller/billing.go)、[充值交互](../../web/src/features/recharge-flow.tsx)、[后台 quota 调整](../../controller/user.go)。

### 3.7 账户与认证（M5）

**已有基础：** 用户名密码注册登录、密码与资料邮箱修改、会话管理、安全事件、账号注销。

**主要缺口：**

- 手机号注册与绑定、短信验证码校验、短信登录和找回密码。
- 真实短信及验证邮件通道。
- 登录失败锁定、人机验证等 PRD 规定的认证防刷能力。

当前登录与注册界面已明确说明短信、验证邮件和密码找回不可用。资料邮箱修改不代表邮箱验证或邮件认证已完成。

代码依据：[注册与登录](../../controller/user.go)、[认证界面](../../web/src/pages/auth/auth-dialog.tsx)、[账户安全界面](../../web/src/features/account-security.tsx)。

### 3.8 管理后台安全与凭证保护（M7、M10）

### 3.12 上线保障、影子验证与开源交付（M10）

**已有基础：** 构建与测试 CI、Docker、配置热更新、渠道健康检查、指标及渠道告警。

**尚缺实现或交付证据：**

## 五、看板状态及文档口径需要校准的内容

1. **接口契约：** 看板关联任务已全部登记完成，但本地代码未找到商业版真实同步、遥测、探测等完整实现，不能直接沿用完成结论。
2. **Key 周期：** 看板存在已完成的周期重置任务，而当前适配器明确说明后端没有周期概念。
3. **账户认证：** 看板关联任务已全部登记完成，但最新版需求要求的短信认证与找回密码仍不可用。
4. **地区档案：** 看板关联任务已全部登记完成，但现有资源地域模型不能替代完整地区档案。
5. **凭证加密：** 看板有已完成的加密与轮换任务，当前 Key 存储尚未体现相应实现。
6. **资源投放：** 当前代码已有大量后端实现，不能沿用早期文档中「仅 localStorage 演示」的判断。
7. **视频任务：** 需求保留且代码已有实现，但有效关联任务为空，不能以任务数为零推断功能已完成或无需工作量。
8. **重复任务：** 同一功能同时存在汇总任务与细项，重新排期前应先去重，再核实实现与验收剩余量。

仓库中的 [未实现能力登记](../../testdata/blocked-capabilities.json) 也存在历史信息，尤其资源投放条目已落后于当前代码，不能单独作为最终判断依据。

以下两项应按最新版 PRD 排除出首发缺口：

- 智能入口的「最快／最稳」策略已经明确推迟至后续版本，1.0 首发仅要求「最省」。
- 后台加款双人复核已撤回，首发要求单人执行并留审计痕。

视频和阿拉伯文的去留仍应按项目决策记录确认；本次未擅自将其移出交付范围。

## 六、建议推进顺序

此顺序为本次分析建议，不代表已修改看板优先级或排期。

1. **先明确交付边界与接口：** 商业版架构、资源平台真实契约、视频与阿拉伯文范围。
2. **打通资源与路由：** 资源同步、算法快照、P/Q/G 过滤、评分流量池、熔断降权与遥测。
3. **打通账务与支付：** 统一金额刻度、可信资金与调用额度、消费流水、加款退款和每日对账。
4. **补齐 Key 与认证安全：** 周期额度、独立智能入口配置、重复查看 Key、凭证加密、短信认证及后台 2FA。
5. **完成交付验收：** 地区档案、真实状态与告警、压测、恢复演练、安全合规、影子验证和开源发布。

## 七、验证范围与限制

- 远程数据库使用只读连接读取；未修改远程代码、任务状态、数据库业务内容或服务配置。
- 本次为代码与需求静态核对，未执行真实短信、支付、资源平台或供应商联调。
- 未执行压测、容灾演练、安全扫描或完整 PRD 验收，不将已有测试文件等同于验收通过。
- 「未找到实现」指本次核对的 StarHub 代码范围，不排除相关工作存在于其他仓库、分支或未合入代码中。
- 954 小时是看板登记值，不是本次重新估算的剩余工时；本文不输出功能完成百分比。
