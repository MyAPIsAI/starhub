# 中转站 P0 原型分析（基于 new-api 代码库）

## 一、端到端链路

```
客户端 sk-xxx ──POST /v1/chat/completions──▶
  TokenAuth (验 key) ──▶ 确定使用分组 ──▶ Distribute (按 分组×模型 选渠道) ──▶
    Relay (协议转换) ──▶ 上游 API (渠道 key) ──▶ 响应回传 + 计费扣额
```

## 二、五个环节的代码映射与最小集

### 1. 设置分组
| 概念 | 代码位置 |
|---|---|
| 用户分组字段 | `model/user.go:100` `User.Group`（默认 `default`） |
| 分组倍率（计费） | `setting/ratio_setting/group_ratio.go:12` |
| 用户可用分组（token 能否切组） | `setting/user_usable_group.go` |
| 渠道侧分组 | `model/channel.go:40` `Channel.Group` |

分组本质是**三方约束**：`用户.Group` / `Token.Group` → `Channel.Group`，通过 `abilities` 表（`model/ability.go:18`，`group+model+channel_id` 联合主键）建立倒排索引。**P0 最简：全部用 `default` 分组，只保留 group_ratio 一张表用于倍率。**

### 2. 配置渠道
- 结构：`model/channel.go:23`（Type/Key/BaseURL/Models/Group/Status/Priority/Weight/ModelMapping）
- 创建链：`controller/channel.go` AddChannel → `model/channel.go:522` `Insert()` → `model/ability.go:204` `AddAbilities()`（为每个 group×model 写一行）→ 渠道缓存重建 `model/channel_cache.go`（`group2model2channels` 内存索引）
- 协议适配：`relay/channel/adapter.go:16` Adaptor 接口 + `relay/relay_adaptor.go:56` 按类型分发（40+ 适配器）

**P0 最简：只保留 1 个适配器（OpenAI 格式，type=1），单 key、无 ModelMapping、无 ParamOverride、无多 Key。**

### 3. 设置 API Key（令牌）
- 结构：`model/token.go:14`（Key/UserId/Status/ExpiredTime/RemainQuota/UnlimitedQuota/Group）
- 创建：`controller/token.go:264` AddToken → `common.GenerateKey()` 生成 `sk-` 前缀 key
- key 格式暗藏功能：`sk-<key>-<channelId>`（`middleware/auth.go:515`，管理员可指定渠道重试，P0 可砍）

**P0 必留字段：Key、UserId、RemainQuota、Status；可砍：ModelLimits、AllowIps、AutoGroups、CrossGroupRetry。**

### 4. API 鉴权
核心在 `middleware/auth.go:352` `TokenAuth()`：
1. 多协议取 key：`Authorization: Bearer`（OpenAI）、`x-api-key`（Claude）、`x-goog-api-key`/query `key`（Gemini）、WebSocket Protocol 头
2. `model/token.go:220` `ValidateUserToken`：状态/过期/额度三查
3. 用户状态校验（`GetUserCache`）
4. 分组裁决：`token.Group` 非空则校验 `GetUserUsableGroups` + `ContainsGroupRatio`，否则回退用户分组 → 写入 `ContextKeyUsingGroup`（auth.go:458-475）

**P0 最简：只支持 Bearer 头，查库（无 Redis）验证。**

### 5. Token 中转
两段式：

**选路** — `middleware/distributor.go:35` `Distribute()`：
- gjson 从 body 提取 `model`（distributor.go:284）
- `service.CacheGetRandomSatisfiedChannel` → `model/channel_cache.go:117`：优先级降序取最高层 → 层内按权重加权随机
- `distributor.go:506` `SetupContextForSelectedChannel`：渠道 key/BaseURL/Type/Mapping 注入 context

**转发** — `controller/relay.go:73` `Relay()`：
- 按 RelayMode 分发（`relay/compatible_handler.go:25` TextHelper 为最核心路径）
- 流程：ModelMapping → `adaptor.ConvertOpenAIRequest` → `DoRequest`（替换上游 key）→ `DoResponse`（流式/非流式）→ **计费**
- 计费：预扣 + `service/text_quota.go:397` `PostTextConsumeQuota`（usage × 模型倍率 × 分组倍率 → 扣 token/user quota → 写 Log）

## 三、P0 最小数据模型（5 张表）

| 表 | P0 必要字段 |
|---|---|
| users | id, username, password, role, quota, `group` |
| tokens | id, user_id, key(unique), status, remain_quota, unlimited_quota |
| channels | id, type, key, base_url, models, `group`, status, priority, weight |
| abilities | group+model+channel_id 复合主键, enabled（**路由索引，不可省**） |
| logs | user_id, token_id, model, prompt/completion tokens, quota |

## 四、P0 可裁剪清单

- ❌ auto 分组/智能路由/渠道亲和（distributor.go:132-162 整段）
- ❌ 多 Key 渠道、跨分组重试、令牌模型限制、IP 白名单
- ❌ MJ/Suno/视频任务、realtime WS、Responses/embedding/audio（只留 `/v1/chat/completions` + `/v1/models`）
- ❌ Redis 缓存层（直接查库即可）、支付/邀请/OAuth/Passkey
- ⚠️ **不可裁剪**：abilities 索引、quota 扣减与 log（否则是纯代理而非中转站）、渠道禁用自动检测（最起码保留手动 status 开关）

## 五、最小闭环验证路径

```
1. root 登录 → 运营设置 group_ratio={"default":1}
2. POST /api/channel/ → type=1, key=上游sk, models="gpt-4o-mini", group="default"
3. 用户充值 quota → POST /api/token/ → 得到 sk-xxx
4. curl /v1/chat/completions -H "Authorization: Bearer sk-xxx" -d '{"model":"gpt-4o-mini",...}'
5. 验收点：响应正常 ✓ token.remain_quota 下降 ✓ channels.used_quota 上升 ✓ logs 有记录 ✓
```

整条链路的耦合点只有两个 context key：`ContextKeyUsingGroup`（auth 写、distributor 读）和渠道五元组（distributor 写、Relay 读）——这也是做 P0 原型时唯一需要严格守住的数据契约。
