# P7.1 图片测试报告:可用性实测 + 内存单份持有可行性分析

> 状态:实测完成 + 方案分析(2026-09-23)
> 结论先行:
> ① **图片生成中继功能可用**——JSON/SSE 双路径、单图/多图、计费闭环全部正确;网关自身开销毫秒级,内存无泄漏,并发 86 req/s。
> ② **「图片在服务内存中只保留一份」可行**——当前 JSON 路径同时持有 ~2 份、SSE 路径 ~3 份、上传路径 ~2 份;经微基准逐段量化后,三条路径均可收敛到 1 份(响应侧),其中 SSE 路径用复用缓冲可达「稳态 0 份、瞬时 ≤1 份」,严格优于目标。改造点明确、风险可控,预计一天工作量。

## 第一部分:可用性与性能实测

### 1. 测试目的与范围

验证 StarHub 图片生成中继(`/v1/images/generations`,P3.1 实现):

1. **能否生成**:JSON 非流式 / SSE 流式,单图与多图(n=2)
2. **响应时间**:按尺寸、数量、流式与否分组的延迟分位数
3. **内存占用**:堆稳态、每请求分配量、峰值、GC 行为
4. **并发吞吐**:多 worker 下的成功率与 req/s
5. **计费正确性**:预扣-结算-退款闭环

不在范围:真实上游推理耗时与图片质量(用确定性 mock 隔离网关开销)。

## 第二部分:能否让图片在服务内存中「只保留一份」

### 6. 现状拷贝路径逐段追踪(以 800KB 图 / 1.09MB b64 载荷为例)

先用微基准(临时基准,数据测毕已删)量化每个环节的分配:

| 环节 | 代码位置 | 实测分配 | 结论 |
| --- | --- | --- | --- |
| 上游响应读入 `io.ReadAll` | `relay_image.go:178` | **2.28 MB/op**(2.1×载荷) | 最终缓冲 1 份 + 倍增扩容丢弃 ~1 份 |
| JSON 计费解析 `ParseImageResponse` | `relay_image.go:184` → `dto/image.go:246` | **1.10 MB/op**(1.0×载荷) | `json.Unmarshal` 把 `b64_json` 物化为完整字符串——**仅用于数数** |
| SSE 事件解析 `ParseImageStreamEvent` | `relay_image.go:254` → `dto/image.go:264` | **2.20 MB/op**(2.0×载荷) | `[]byte(line.Data)` 转换 1 份 + Unmarshal 物化 `B64JSON` 1 份——**该字段是死重量,计费从未读取** |
| SSE 行读取 `SSEReader.Next` | `channel/sse.go:30` | **3.32 MB/op**(3.0×载荷) | `ReadString` 累积抖动 ~2 份 + `strings.Builder` 1 份 |

汇总各路径的**同时在堆上的峰值拷贝数**:

| 路径 | 拷贝构成 | 峰值持有 |
| --- | --- | --- |
| JSON 响应(generations) | body 缓冲 + 解析出的 b64 字符串 | **~2 份**(外加 ReadAll 扩容抖动) |
| SSE 响应(generations,流式) | line.Data 字符串 + []byte 转换 + 解析 b64 字符串 | **~3 份/事件**( churn 共 ~5 份) |
| JSON→SSE 包装(`imageJSONasSSEAttempt`) | body + 解析字符串 + 再 marshal | ~3 份 |
| 上传(edits 请求侧) | Distribute 缓存的原始 body + `ParseMultipartForm` 对每个文件 `ReadAll`(`common/multipart.go:102`) | **~2 份** |

这解释了 4.1 中流式比非流式慢一倍(每事件 4 次全量拷贝、两次 4.4ms 级的 Unmarshal),以及 4.3 的 GC 频次。

### 7. 可行性结论:**可以,且三条路径都能做到**

#### 7.1 JSON 响应路径 → 精确 1 份(低风险,收益 −67% 分配)

1. **预分配读缓冲**:按 `Content-Length` 预尺寸(或 `sync.Pool` 取池化缓冲),消灭 ReadAll 倍增抖动:2.28MB → 1.09MB。该缓冲即**唯一的一份**。
2. **元数据式计费解析**:替换 `ParseImageResponse` 的整串物化——把 `data[]` 条目解成 `struct{ URL, B64JSON json.RawMessage }`(`RawMessage` 只引用输入切片,**零拷贝**),`Count()` 判 `len()>0` 且非 `null`,`Usage` 照常解。字符串物化 1.10MB → ~0。
3. 结果:堆上恰 1 份(body 缓冲),写客户端直接 `w.Write(body)`(net/http 大块写不进堆缓冲)。

> 为什么不做 0 份(TeeReader 边收边转)?响应必须「先验证再提交」以保留 failover/中止语义——首字节发出后无法换渠道重试。1 份是该语义下的下限,建议保留。

#### 7.2 SSE 响应路径 → 稳态 0 份、瞬时 ≤1 份(严格优于目标)

1. **去掉死重量**:删除 `ImageStreamEvent.B64JSON`(`imageStreamAttempt` 只消费 `Type/Usage/ErrorMessage`,见 `relay_image.go:254-266`),`b64_json` 解为 `RawMessage` 或直接跳过 → 省 1 份 + 4.4ms/事件。
2. **消灭 string↔[]byte 往返**:`SSEReader` 增加 `NextBytes() ([]byte, error)` 变体(`SSELine.Data` 改 []byte 会波及 openai/claude/gemini 聊天流式共 5 处调用点,**加变体不动旧 API** 风险最低);`writeFrame` 改 `w.Write(data)` 直写。
3. **事件缓冲复用**:同一连接的每次 `NextBytes` 写入同一块复用缓冲(「单属主缓冲」,有效期内不被复用),行读取的 Builder 分配归零。
4. 结果:图片完整驻留堆的时刻仅存在于 socket→缓冲→socket 的搬运瞬间,稳态占用与事件数无关。

#### 7.3 上传(edits)路径 → 精确 1 份(中风险)

1. Distribute 缓存的原始 body 是**架构上必须保留的一份**(重试逐字重放,`distributor.go` 的既定契约),它就是那 1 份。
2. `ParseMultipartForm` 改元数据式:文件 part 只读 header,**内容用计数 reader 跳过**(`io.Copy(io.Discard, part)` 累计字节数),`FileBytes()` 供 STT 计费改读计数——不再 `ReadAll` 出第二份。
3. (可选加固)超过阈值(如 8MB)的请求体落盘临时文件重放,堆上 0 份,代价是磁盘 I/O——new-api 对大上传即此做法;当前 32MB 上限下单机内存充足,可暂不做。

### 8. 做不到/不该做的部分(边界说明)

| 项 | 原因 |
| --- | --- |
| 请求侧 0 份(不落盘) | 重试重放契约要求完整持有请求体 |
| 响应侧 0 份 | 先验证再提交(failover)语义要求完整缓冲 |
| 内核 socket 缓冲/TLS | Go 堆之外,任何实现都存在 |

### 9. 预期收益与实施建议

| 指标 | 现状 | 预期 |
| --- | --- | --- |
| JSON 路径网关侧分配 | ~3.4 MB/图(3.1×) | **~1.1 MB(1×)** |
| SSE 路径 churn | ~5.5 MB/事件 | 稳态 ~0(复用缓冲) |
| 流式 p50(1024x1024) | 30.6 ms | 预计 12~18 ms(两次 4.4ms Unmarshal 退出) |
| 非流式 p50 | 13.6 ms | 预计 8~11 ms |
| GC 频次 | ~3 次/请求 | ~1~1.5 次/请求 |

**实施顺序**(均有现成 e2e 兜底:`TestP3ImageGenerations` / `TestP3ImageOverAndUnderDelivery` 覆盖计费不变量):

1. 删 `B64JSON` 死字段 + RawMessage 化(半天内,零行为变化,收益最大)
2. JSON 路径:预分配缓冲 + 元数据式 `ParseImageResponse`
3. SSE:`NextBytes` 变体 + 复用缓冲 + 直写
4. 上传路径元数据式解析(注意 `FileBytes` 计费口径,配单测)
5. (可选)`sync.Pool` 缓冲池 + 在途响应字节总量信号量(64MB × 并发的爆炸半径控制)

**总评估:约 1 人日,风险低,建议纳入 P2.1 计费缺口修复后的下一个迭代。**

## 第三部分:落地记录(2026-09-23 已实施)

按第七节方案完成实施,**四条路径的存活拷贝数全部收敛到 ≤2**:

| 路径 | 改造前存活拷贝 | 改造后 | 实现方式 |
| --- | --- | --- | --- |
| JSON 响应(计费解析) | 2(n=1)/ 3(n=2) | **2**(body + 1 份临时 data 数组拷贝) | `dto.WalkImageResponse`:头对象解出 data 数组一次拷贝,条目 url/b64 用**原地扫描器**切字引用,不再物化字符串 |
| JSON→SSE 包装 | ~3 | **2** | 帧segment直写(`head + raw + mid + tail`),raw 值切片引用 data 拷贝 |
| SSE 流式 | ~3/事件(churn ~5.5) | **1**(复用缓冲,稳态 0 新分配) | `channel.SSEByteReader`:data: 行经 peek 分类后**直读进复用缓冲**;计费解析用 `ParseImageStreamEventMeta`(b64 扫描但永不物化) |
| 上传(edits/STT) | 3(body + distributor 全量拷贝 + 控制器全量拷贝) | **1**(缓存的原始 body) | `common.ParseMultipartFormMeta`:文件经 `io.Discard` 计数,distributor 与控制器均不再物化文件内容 |

另:`readBoundedBody` 对带 Content-Length 的响应做单次精确分配(消除 io.ReadAll 倍增抖动;chunked 响应回退 ReadAll,行为不变)。

### 改动文件

- `relay/dto/image.go` — `WalkImageResponse` / `ImageEntryRaw` / `RawStringLiteral` / `ParseImageStreamEventMeta`(原地 JSON 扫描器:`scanJSONValueEnd` 等)
- `relay/channel/sse.go` — `SSEByteReader`(不影响 openai/claude/gemini 既有 `SSEReader` 调用方)
- `controller/relay_image.go` — 三个 attempt 重写;edits 切元数据解析
- `controller/relay_passthrough.go` — `readBoundedBody`;STT 切元数据解析
- `common/multipart.go` — `MultipartFormMeta` / `ParseMultipartFormMeta`(旧全量解析保留供 e2e 断言用)
- `middleware/distributor.go` — multipart 分支切元数据解析
- 测试:`relay/channel/sse_bytes_test.go`、`relay/dto/image_meta_test.go`、`common/multipart_meta_test.go`

### 语义保证(稳定性验证)

- **计费语义完全对齐**:`WalkImageResponse` 与旧 `ParseImageResponse` 在 21 种形态(空串/null/缺 data/拆分条目/类型错误/尾随垃圾/重复键 last-wins…)上逐一对照测试(含 `created` 类型检查);`ParseImageStreamEventMeta` 与旧解析器逐字段对照
- **计费不变量 e2e 全绿**:`TestP3ImageGenerations` / `OverAndUnderDelivery` / `EditsMultipart` / `JSONasSSE` / `StreamOverDelivery` / `StreamClientDisconnect` 全部通过,含精确扣费断言
- 唯一有意偏离:条目内非计费字段(如畸形的 `revised_prompt`)不再导致整响应计 0,而是按实际交付计费——收入安全方向(反逃费)
