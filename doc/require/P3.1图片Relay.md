# P3.1 图片 Relay：让中转「会画图」

图片生成与文本聊天在**请求形态（JSON + multipart）、计费模型（按张计价）、响应体（base64/URL/SSE）**三个维度都不同，是 P3 多协议扩展里第一个要落的专项。参考实现全部来自 new-api 生产代码。

## 一、路由入口

`router/relay-router.go:113-121`：

```
POST /v1/images/generations  → RelayFormatOpenAIImage（文生图）
POST /v1/images/edits        → RelayFormatOpenAIImage（图生图/局部重绘，multipart）
```

复用 P0 已有的 `TokenAuth → Distribute → Relay` 主链路，`Distribute` 对 `/v1/images/generations` 无 model 时兜底 `"dall-e"`（`middleware/distributor.go:430-441`，edits 从 multipart 表单提取 model）。

## 二、请求验证与 DTO

### 2.1 双格式解析
`relay/helper/valid_request.go:182` `GetAndValidOpenAIImageRequest`，按 relayMode 分流：

| 路径 | 格式 | 解析方式 |
|---|---|---|
| generations | JSON | `UnmarshalBodyReusable`（可重放） |
| edits | `multipart/form-data` | `ParseMultipartFormReusable`（表单+文件缓存，重试可重放） |

### 2.2 DTO 设计要点（`relaykit/dto/openai_image.go:17`）
- `N *uint`、`Stream *bool`、`Watermark *bool`——**可选标量一律指针 + omitempty**（工程纪律第 2 条的直接体现）
- 其余供应商私有字段（`background`/`moderation`/`watermark_enabled`…）用 `json.RawMessage` 透传，不感知语义
- 自定义 `UnmarshalJSON` 把未知字段收进 `Extra` map：**OpenAI 格式之外的字段原样透传给上游**（智谱、Midjourney 风格参数不丢失）
- 匿名参数合并进 `extra_fields`，序列化时平铺回去

### 2.3 验证规则（计费安全的第一道闸）
```
n        ∈ [1, MaxImageN=128]   ← JSON 路径和 multipart 路径都要查（valid_request.go:199/249）
size     dall-e-2: 256/512/1024 平方；dall-e-3: 1024/1024x1792/1792x1024
quality  默认值按模型补齐（dall-e-3=standard, gpt-image-1=auto）
全角 ×   拒绝，提示用 x
```
`MaxImageN` 的存在原因（dto 注释原话）：*无上界的 n（含回绕负数）会溢出计费为负数=送钱*。multipart 路径的 `n` 是字符串表单字段，`strconv.Atoi` 后同样卡界——**旁路（multipart/passthrough）必须与主路径同界**。

## 三、转发流程

`relay/image_handler.go:23` `ImageHelper`，与 `TextHelper` 同构：

```
ModelMappedHelper（模型名映射）
→ adaptor.ConvertImageRequest（协议转换）
→ [可选 ParamOverride 注入]
→ DoRequest（替换上游 key，multipart 原样重组）
→ DoResponse（按流式/非流式分发）
→ PostTextConsumeQuota（结算，携带 大小/品质/数量 日志字段）
```

差异点：
- 转换产物可能是 `*bytes.Buffer`（multipart 重组后）而非 JSON，handler 需按类型分支
- `RelayErrorHandler` 处理非 200；Replicate 渠道 `201 Created` 视为成功（`image_handler.go:101`）
- usage 兜底：上游不返回 usage 时 `TotalTokens=1`，保证日志行不为空

## 四、计费模型（P2 三段式在图片上的落地）

### 4.1 估算阶段（预扣）
`ImageRequest.GetTokenCountMeta()`（dto/openai_image.go:133）：

```
ImagePriceRatio = sizeRatio × qualityRatio     ← 尺寸×品质（dall-e-3 hd=2.0 等）
BillingRatios   = {"n": 请求数量}               ← 张数独立维度
```

**关键设计**：`n` 与 `ImagePriceRatio` 刻意分离（dto:162 注释），尺寸品质和数量是两个独立计费维度，预扣时分别写入 `PriceData.OtherRatios`：

```
预扣 = 模型按次价 × ImagePriceRatio × n × 分组倍率
     （price.go:127-128, price.go:167-171 ApplyOtherRatios）
```

### 4.2 结算阶段（按实际张数修正）
`relay/channel/openai/relay_image.go:25` `updateOpenAIImageCount`：用**上游实际返回的 `data.#` 数量**替换预扣时的 n。带防绕过护栏：
- 仅 `UsePrice`（按次计价）时生效
- `count <= 0 || count > MaxImageN` 直接忽略（不更新，保持请求值）——防上游异常数据污染账本

流式路径按 `image_generation.completed` 事件计数，且有两条**法院判例级的计费不变量**（`image_stream_test.go:223-282`）：
1. **客户端中途断开不得降低计费张数**——用户请求了 3 张，收到 1 张主动断连，仍按 3 张计费（防"看一眼就跑"白嫖）
2. **上游多给必须加价**——断连后仍收到第 2 张 completed，n 从 1 提升到 2，向上取实际值

### 4.3 usage 归一化
`normalizeOpenAIUsage`（relay_image.go:70）：图片 API 返回 `input_tokens/output_tokens`，映射到全局统一的 `PromptTokens/CompletionTokens`。注释明确警告：**overwrite 语义仅限图片路径，禁止照搬到 chat/embedding**（防双计）。

## 五、流式图片（SSE）

gpt-image-1 支持 `stream=true`，事件序列（`OpenaiImageStreamHandler`，relay_image.go:93）：

```
event: image_generation.partial_image   （渐进预览，不计费）
event: image_generation.completed       （完成一张，计一张）
data: {"usage":{...}}                   （终态用量）
```

实现要点：
- 复用 chat 流式的 keepalive/超时设施（`info.IsStream` 由响应 Content-Type 或请求 `stream` 决定）
- **JSON 响应包装成 SSE**（`openaiImageJSONAsStreamHandler`，relay_image.go:234）：上游不支持流式但客户端要流式时，把 JSON 拆成 N 个 completed 事件逐个推送——中转站对客户端的协议承诺优先于上游能力
- 错误事件（`isOpenAIImageStreamErrorEvent`）要识别并转成正常错误返回，不能当数据透传

## 六、易踩的坑（本仓库已付过学费）

| 坑 | 规则 |
|---|---|
| multipart 的 n 是字符串 | 两条解析路径都要卡 `[1, MaxImageN]`，回归测试挂在验证器上（`openai_image_request_test.go` 风格） |
| 客户端断连少收钱 | 断连不降 n；多收到 completed 必须升 n |
| 回绕负数 | `*uint` 收 `18446744073686646784` 这种值，上界检查必须显式 |
| usage 双计 | 图片路径的 usage 归一化用 overwrite，勿复用到 chat |
| 透传丢参数 | 未知字段进 `Extra` 原样回传；但 `extra_fields` 与 `Extra` 的合并被明确禁用（dto:88 注释，历史上踩过） |
| 视觉输入 vs 图片生成 | chat 里的图片输入走 `GetImageRatio`（price.go:117，按图片 token 计费），与本文的按张计价是**两套倍率**，不要混用 |

## 七、在整体规划中的位置

```
P0 闭环       ：只有 /v1/chat/completions
P3.1 (本文)   ：+ /v1/images/generations + /v1/images/edits          —— 验证 multipart/按张计价/SSE 三项新能力
P3 后续       ：其他渠道的 ConvertImageRequest 适配（智谱/Replicate/Gemini 图像）
                任务型图像（MJ/Kling/即梦）走 TaskAdaptor 而非本文路径
```

交付物：图片生成/编辑双端点、multipart 可重放、按张计价与预扣结算闭环、流式图片 SSE、计费边界回归测试。
