# 事件公告刷新丢失：分析与分项修复

日期：2026-11-19

## 1. 问题、原因与修复顺序

截图 [ee1.png](../ee1.png) 对应 `/admin?tab=incidents`：新公告在点击发布后立即显示，刷新后整张公告卡片消失。根因是管理页仍用 `useState([])` 保存公告，`handlePublishIncidentSubmit` 只把标题、正文、供应商和写死的 `investigating` 状态加入页面内存，再关闭弹窗；没有发送保存请求，刷新时也没有读取后台列表。代码中“公告没有后端接口”的注释已经过时。后端现有 `ServiceIncident`、`ServiceIncidentUpdate` 两张表及创建、列表、详情、状态更新和公开查询接口，数据库迁移也已包含它们。本次分析时只读检查本地 `starhub-dev.db`、`starhub.db`，公告数均为 0；实际开发代理 `/api/status/incidents` 返回成功和空列表，与前端没有写入后台一致。

公开状态页 `/status` 另从 `useProductPreview.incidents` 读取演示公告，未连接持久化数据。因此只替换管理页内存还不够，公开页也要读取同一后台来源。红框中的 `Investigating` 是原始英文状态值，需统一显示为调查中、已定位、监测中、已解决，并使用后台真实更新时间。既往仅留在页面内存、已经刷新的公告没有写入数据库，需要重新发布；新增浏览器本地缓存不能解决跨账号或公开页面的数据一致性。

代码依据：

- [管理页](../web/src/pages/admin/index.tsx)：原公告状态、发布函数和弹窗。
- [公开状态页](../web/src/pages/status.tsx)：原演示数据读取。
- [公告控制器](../controller/incident.go)、[公告模型](../model/service_incident.go)：已有持久化和查询能力。
- [路由](../internal/router/router.go)：管理接口已有管理员鉴权和审计，公开查询允许匿名访问。

按以下顺序修复，每项验证后单独提交，P27 文档保留现有修改、不纳入提交：

| 顺序 | 修复内容 | 最小实现和验收 |
| --- | --- | --- |
| 1 | 后台保存与读取 | 新增前端公告 API hooks，管理页读取 `GET /api/incident`，发布调用 `POST /api/incident`；标题、说明、供应商分别映射 `title`、`description`、`component`。明确发布成功后才关闭弹窗，失败保留草稿；提交期间防止重复点击；刷新后仍可读到同一公告。 |
| 2 | 公开状态页同步 | `/status` 改读 `GET /api/status/incidents`，沿用后台“未解决和最近七天已解决公告”的筛选。发布后刷新公开页及匿名访问均可读取；接口失败不回退到演示公告。 |
| 3 | 展示反馈与本地化 | 管理页和公开页补加载、空列表、读取失败和重试；统一四种状态的中英阿显示、供应商标签和真实更新时间；检查窄屏、深浅主题、键盘和滚动。 |

复用现有数据库和后端接口，不新增公告存储表，不扩展编辑、删除或多语言存储；原文按管理员实际输入展示。列表兼容后端空集合返回 `null` 的情况。新增状态查询与当前登录身份隔离，公开列表独立缓存，发布成功刷新相关缓存。公开页的其他服务质量或模型展示不属于本次公告修复。

验收使用独立临时数据库与本地服务，不向正在使用的开发库发布测试公告。重点验证发布失败保留输入、请求未完成时不显示成功、刷新和跨页后仍存在、公开页匿名可见，以及空列表、失败、重试和四种状态。修改前执行公告模型测试已通过；后续执行记录随各项修复更新。
