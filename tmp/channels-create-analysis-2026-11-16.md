# 渠道管理新增入口与自定义渠道接入分析

日期：2026-11-16。

分析依据：`cc1.png` 与当前工作区源码。本次仅新增本文档，未修改业务代码、创建渠道、写入数据库或请求上游服务。真实密钥不记录在本文档中。

## 一、当前页面为什么没有新增渠道按钮

`/console/channels` 通过 `web/src/features/channels.tsx` 加载 `ResourceInventory`，实际展示“渠道资源与投放”。

该页面负责导入资源快照、维护资源实例的模型映射与分组投放，以及预览和发布网关绑定。顶部现有操作为刷新、导入快照、网关发布预览和区域目录，没有接入真实渠道创建表单。截图与当前源码一致。

页面提示区已有“打开后台渠道”链接，目标为 `/admin?tab=resources`。该后台资源页已提供真实渠道列表、“新建渠道”、编辑、删除和测试连通能力。缺少新增按钮属于当前页面的功能入口未整合，不代表系统尚未实现渠道创建。

主要证据：

- `web/src/features/channels.tsx`：渠道页面入口。
- `web/src/features/resource-inventory.tsx`：顶部操作、后台渠道链接、资源列表和发布区域。
- `web/src/pages/admin/index.tsx`：真实渠道列表及创建、编辑弹窗。
- `web/src/main.tsx`：`/admin/*` 路由仍存在，并受登录及管理员权限限制。

历史 `web/HANDOFF.md` 中“无独立后台、无真实网关”等描述属于旧演示阶段，与当前代码不一致；本分析以当前路由、控制器和数据模型为准。

## 二、是否可以在当前页增加功能

可以，基础创建能力已经存在：

| 层级 | 现有实现 | 可复用内容 |
| --- | --- | --- |
| 前端表单 | `web/src/pages/admin/index.tsx` | 类型、名称、密钥、模型、分组及上游地址 |
| 前端接口 | `web/src/lib/api/channel.ts` | `useCreateChannel()`、编辑和删除 hooks，以及相关查询缓存失效 |
| 后端路由 | `internal/router/router.go` | `POST /api/channel`，管理员鉴权及审计 |
| 创建控制器 | `controller/channel.go` | 类型、模型、分组、地址和状态等处理 |
| 数据模型 | `model/channel.go` | 事务内保存渠道并重建路由能力 |

现有类型包括 OpenAI、Claude、AWS Bedrock、Gemini 和视频任务插件。普通的 OpenAI 兼容供应商可通过 OpenAI 类型配合自定义上游地址接入，无需新增供应商类型。

仅把真实渠道创建能力接入当前页面，通常不需要新增数据库表或后端创建接口。

## 三、真实渠道与资源快照的边界

| 对象 | 主要内容 | 创建真实渠道后的变化 |
| --- | --- | --- |
| 真实渠道 | 上游凭证、地址、类型、模型、分组及状态 | 新增一条渠道记录，按配置生成普通渠道路由能力 |
| 资源快照 | 来源渠道、资源实例、能力、区域及投放清单 | 不会因真实渠道创建而自动生成 |
| 发布绑定 | 来源渠道与真实渠道的显式关联及准确模型/分组组合 | 需要资源清单、投放配置及明确预览发布 |

因此，新增真实渠道后，截图里的“0 个资源”仍可能保持不变；新渠道可出现在网关发布上下文的真实渠道候选列表中。不能用资源数不变判断渠道创建失败。

普通渠道直接使用配置的模型和分组；托管渠道使用资源页明确发布的准确组合。普通渠道接入不要求先导入资源快照。

需要特别区分创建与发布：现有后台表单默认 `status: 1`，创建后会生成启用的普通渠道路由能力，可能进入实际调用候选；不能把所有渠道创建都描述为“等待资源发布”。

证据：`model/ability.go`、`model/resource_catalog.go`、`model/resource_publication.go`、`web/src/features/channel-routing-notice.tsx`。

## 四、建议的页面改造范围

1. 在 `/console/channels` 顶部增加固定的“新增渠道”主按钮，抽取并复用现有创建表单。
2. 增加真实渠道列表或页签，提供编辑、启停及测试入口，让创建成功后有明确落点。
3. 保留资源快照、模型映射、投放与发布流程，并显示真实渠道的关联状态。
4. 明确提供启用状态选择；如果产品流程要求先测试再上线，可默认禁用并由管理员主动启用。
5. 补齐接口失败提示、提交中保护和成功后的查询刷新。当前创建弹窗没有明确展示创建失败结果，不能只移动现有代码而忽略反馈。
6. 创建入口不应依赖已有资源快照；没有快照时也应能创建普通渠道。

第一阶段建议完成“当前页新增真实渠道 + 渠道列表”的操作闭环。自动生成来源渠道、资源实例、绑定与投放属于进一步整合，需要额外处理资源必填字段、版本冲突及明确发布规则。

现有表单虽然初始化了 `status`、`priority`、`weight` 和 `key_mode` 等字段，但没有对应的完整编辑控件。建议增加状态选择是后续改造建议，并非当前页面已有能力。

## 五、本次自定义渠道应如何填写

用户提供的服务地址为 `http://103.186.215.40:3000/v1`。以下方案以该服务支持 OpenAI 兼容聊天接口及 Bearer 密钥认证为前提；未访问服务，兼容性和密钥有效性尚未验证。

### 1. 地址必须去掉末尾 `/v1`

当前 OpenAI 适配器的聊天 URL 构造方式是：

```text
trimBase(base_url) + "/v1/chat/completions"
```

`trimBase()` 只清除空白和末尾斜杠，不会清除 `/v1`。因此：

| 渠道中填写的 base_url | 当前代码生成的聊天请求地址 |
| --- | --- |
| `http://103.186.215.40:3000` | `http://103.186.215.40:3000/v1/chat/completions` |
| `http://103.186.215.40:3000/v1` | `http://103.186.215.40:3000/v1/v1/chat/completions` |

本次应填写 `http://103.186.215.40:3000`。

现有表单的上游地址占位提示为 `https://api.openai.com/v1`，与聊天适配器实际拼接规则不一致，后续应修正提示，或统一适配器的路径规范化。Responses 地址有单独处理逻辑，不能据此推断聊天、图片及其他接口都接受含 `/v1` 的地址。

证据：`relay/channel/openai/openai.go` 中的 `ChatURL()`、`ModeURL()`、`trimBase()`，以及 `web/src/pages/admin/index.tsx` 的 `ch-base-url` 输入框。

### 2. 现有界面的操作路径

使用已完成管理安全设置的管理员或 Root 账号：

1. 在当前页面点击“打开后台渠道”，或打开本站 `/admin?tab=resources`。
2. 在“渠道列表”右侧点击“新建渠道”。
3. 按下表填写并创建。
4. 在新渠道所在行点击“测试连通”，查看所选模型是否返回成功。

| 表单字段 | 本次建议值或填写方法 |
| --- | --- |
| 渠道类型 | `OpenAI`，对应 `type: 1` |
| 名称 | 例如 `Custom-103.186.215.40`，可自行命名 |
| 密钥 | 在密码输入框中填入用户提供的完整密钥，不附加 `Bearer ` 前缀 |
| 模型 | 填入该上游和该密钥实际可用的准确模型 ID；多个模型使用英文逗号分隔 |
| 分组 | 可使用 `default`，或平台实际配置的目标分组；需与后续调用令牌的分组匹配 |
| 上游地址 | `http://103.186.215.40:3000` |

认证适配器会自行构造 `Authorization: Bearer <key>`，无需用户把认证前缀放进密钥字段。

当前界面默认创建为启用状态，并未提供创建时的状态选择。若希望先禁用创建再测试，可使用已有管理 API 的 `status: 2`；测试成功后再通过更新 API 显式设为 `status: 1`。手动禁用渠道不会因为测试成功自动启用。

### 3. 当前还缺少模型信息

后端要求 `models` 为非空的英文逗号分隔列表。只有 URL 和密钥仍不足以确定可用配置，不能任意填入一个常见模型名。

模型 ID 可以从供应商控制台或文档确认；若供应商实现标准模型列表接口，也可以使用该密钥查询 `GET http://103.186.215.40:3000/v1/models`。该接口是否存在及返回哪些模型，本次未验证，当前新建表单也没有自动拉取上游模型的操作。

下面仅为禁用创建的请求结构示例，不可直接把占位值作为有效渠道配置提交：

```json
{
  "name": "Custom-103.186.215.40",
  "type": 1,
  "key": "<enter the provided key securely>",
  "base_url": "http://103.186.215.40:3000",
  "models": "<actual upstream model ID>",
  "group": "default",
  "status": 2,
  "priority": 0,
  "weight": 1
}
```

请求目标为本站 `POST /api/channel`，使用本站管理员会话。上游密钥只用于渠道凭证，不是本站管理员会话凭证。

### 4. 测试与正式调用的区别

后台“测试连通”会向上游发送一次真实的最小聊天请求，内容为 `ping`，`max_tokens` 为 1，可能产生上游用量；未指定模型时使用渠道配置中的第一个模型。它不能证明所有配置模型或全部接口能力均可用。

正式从 StarHub 调用，还需核对平台调用令牌的分组与模型权限、余额，以及目标模型的计价配置。接入托管资源投放时，还需导入或维护相应资源清单，并显式绑定、预览和发布。

给定上游地址使用 HTTP，实际发送的凭证和请求内容不受 TLS 加密保护；供应商若提供 HTTPS 地址，应优先使用。

## 六、本轮结论与验证边界

现有代码支持通过 OpenAI 类型接入自定义地址，不需要为该 IP 专门开发一种渠道类型。本次地址应填主机及端口，去掉末尾 `/v1`；创建前还需确认准确模型 ID 和实际协议兼容性。

本轮完成截图及源码分析和文档保存，没有执行构建或测试，没有创建真实渠道或验证服务连通性，也没有使用或保存真实密钥。

## 七、自定义渠道接入分析补充（上一轮结论单独归档）

现有系统已具备自定义 OpenAI 兼容渠道接入能力，操作入口为本站 `/admin?tab=resources` 的“新建渠道”。针对给定服务，渠道类型选择 OpenAI，名称可自定义，上游地址填写 `http://103.186.215.40:3000`，密钥填入密码字段且不附加 `Bearer ` 前缀，模型填写上游实际支持并对该密钥开放的准确模型 ID，多个模型使用英文逗号分隔，分组可选择实际配置的 `default` 或其他目标分组。地址必须去掉末尾 `/v1`，因为当前聊天适配器自行追加 `/v1/chat/completions`，原样填写含 `/v1` 的地址会得到 `/v1/v1/chat/completions`；现有地址占位提示与实际拼接规则不一致，后续应修正。仅凭地址和密钥无法确认可用模型，需要供应商后台、文档或其支持的 `/v1/models` 接口提供准确模型列表。现有界面创建渠道默认启用，可能进入实际路由候选；“测试连通”会发出真实聊天请求，默认只测试配置中的第一个模型。该地址使用 HTTP，凭证与内容传输不受 TLS 加密保护。此前及本轮分析均未使用真实密钥请求上游或创建渠道，因此协议兼容性、模型可用性与密钥有效性仍未验证；真实密钥不写入本文档。

## 八、“获取上游模型列表”按钮及功能分析（参考 new-api、cc3.png）

### 1. 截图位置与当前缺口

`cc3.png` 显示的是后台“编辑渠道”弹窗。红框位于“模型（逗号分隔）”标签右侧，不是现有模型按钮。当前输入值为 `glm-5.2`，密钥栏显示“留空则不修改”，上游地址为 `http://103.186.215.40:3000`。这些是截图中的配置状态，不代表模型或连接已经验证可用。

对应代码为 `web/src/pages/admin/index.tsx` 的 `ch-models` 字段。目前只有模型字符串输入框，没有拉取按钮、模型候选列表或上游发现接口。新建和编辑共用该表单，新增功能应同时覆盖两种场景。

现有三个接口不能直接替代此功能：

- 本站 `/v1/models` 返回本站令牌可见的模型，不负责连接任意供应商发现模型。
- `/api/plaza/models` 是本站模型广场数据。
- `/api/channel/models/details` 是面向资源平台的本站渠道目录，使用资源平台鉴权，也不是任意上游查询。

因此，增加可用按钮需要同时补齐前端交互和管理员管理 API，无需为基础发现功能新增数据库表。

### 2. 上级目录 new-api 的实际实现

本轮只读参考 `D:/Workspace/new-api`，未修改该目录。

| 参考位置 | 实际行为 | StarHub 可参考的设计 |
| --- | --- | --- |
| `router/channel-router.go` | 注册 `GET /api/channel/fetch_models/:id` 与 `POST /api/channel/fetch_models`，分别检查操作及敏感写权限 | 区分已保存配置和未保存表单的发现请求 |
| `controller/channel.go` 的 `FetchUpstreamModels()`、`FetchModels()` | 前者按渠道 ID 读取保存配置，后者构建临时渠道后查询 | 密钥不需要先保存才能用于新建预览；编辑可由后端读取存储密钥 |
| `controller/channel_upstream_update.go` 的 `fetchChannelUpstreamModelIDs()` | 按供应商选择端点、认证和解析方式；普通 OpenAI 兼容分支使用 `/v1/models` | 端点和认证按渠道类型适配，不能给所有类型套一个 URL |
| `web/src/features/channels/hooks/use-channel-model-discovery.ts` | 使用 `idle/loading/success/error/stale` 状态和序号，丢弃过期请求结果 | 防止改配置、关弹窗或切渠道后出现旧结果 |
| `web/src/features/channels/components/drawers/channel-mutate-drawer.tsx` | 拉取模型后展示选择区，处理加载、失败、空列表与连接配置变化 | 候选模型与已配置模型分开；允许管理员选择后更新表单 |
| `web/src/features/channels/components/dialogs/fetch-models-dialog.tsx` | 支持填回表单模式和独立保存模式 | 本次建议只采用填回表单模式，统一由外层“创建/保存”持久化 |
| `web/src/features/channels/components/upstream-model-selection.tsx` | 支持搜索、分类、勾选，并保留已有但未出现在上游列表中的模型 | 获取结果不能自动删除已有模型 |

new-api 当前普通渠道编辑主要使用按 ID 获取的已保存配置；高级自定义渠道另有草稿预览。StarHub 若要求“按当前表单地址和密钥获取”，不能简单复制按 ID 获取而忽略尚未保存的改动，也不宜照搬其高级配置、代理、映射及框架依赖。

### 3. 建议的界面与操作流程

在红框处，将字段标题行改为左右布局：左侧“模型（逗号分隔）”，右侧小尺寸次级按钮“获取上游模型”。按钮必须是 `type="button"`，点击时不触发表单保存；拉取期间显示“获取中…”并阻止重复请求。

建议交互顺序：

1. 管理员选择渠道类型，填写或核对地址及密钥后点击获取；模型框可以为空，不应触发整张创建表单的必填校验。
2. 前端向本站管理 API 发请求，由 Go 后端访问上游。浏览器不直连供应商，避免跨域、HTTPS 页面访问 HTTP 上游的混合内容问题及绕过后台权限。
3. 在模型框下方展开有高度限制、可滚动的选择区，展示“获取到 N 个模型”、搜索、勾选、选择全部及已选数量。当前弹窗本身已经滚动，优先使用内嵌区域，避免再叠加一层弹窗。
4. 已有模型默认保留；新发现模型默认不全选。上游暂未返回的原配置应单独标识且保留，不能当作已失效自动删掉。
5. 点击“添加所选模型”后，将勾选项与当前输入内容合并、去重，并用英文逗号填回 `channelForm.models`。如需替换，提供单独明确的“替换当前模型”操作并展示移除影响。
6. 只有外层点击“创建/保存”才调用已有渠道写接口。获取和勾选本身不改变渠道、路由、价格、资源清单、绑定或托管授权。

用户修改模型文本后，合并操作应读取当时最新的文本，避免覆盖请求期间手动输入的内容。保留手工填写作为供应商不提供模型目录时的正常操作方式。

窄屏时标题行允许换行；按钮、选择区及错误消息应覆盖中英阿三语、深浅主题和键盘操作，状态消息使用适当的 `aria-live`。现有地址字段位于模型字段下方，可调整到密钥之后、模型之前，让操作顺序更清楚。

### 4. 建议的后台接口契约

建议第一阶段增加统一的 `POST /api/channel/fetch_models`，同时支持新建和编辑草稿。该命名与参考项目一致，是本分析建议，当前 StarHub 尚未实现。

```json
{
  "channel_id": 123,
  "type": 1,
  "base_url": "http://103.186.215.40:3000",
  "key": "<optional draft key>"
}
```

| 字段 | 约定 |
| --- | --- |
| `channel_id` | 新建省略；编辑时传当前渠道 ID，由后端读取原配置和凭证 |
| `type` | 使用当前表单的类型；首期只开放已实现发现适配的类型 |
| `base_url` | 使用当前表单地址；Go 请求结构可使用指针区分省略与显式留空，空地址按该类型官方默认地址解析 |
| `key` | 新建必填；编辑填了新密钥则使用该草稿值；留空表示申请使用已存凭证，不返回真实凭证给浏览器 |

密钥只放在请求体或后台发往上游的认证头中，不放 URL 查询参数，不写入日志，也不将密钥请求加入持久化前端缓存。

后端需明确实施以下凭证选择规则：

- 新建：使用输入密钥；没有密钥就返回明确提示，不能先创建空壳渠道。
- 编辑且填入新密钥：使用当前草稿地址、类型和新输入密钥，获取过程不保存这些改动。
- 编辑且密钥留空：仅当当前有效地址和类型与已存配置一致时，读取已存密钥进行查询。比较前统一处理空白、尾部斜杠及官方默认地址。
- 编辑时地址或类型改变且密钥留空：要求重新输入要用于新配置的密钥，后端也必须拒绝无凭证的跨配置复用。不能自动把已存密钥发送到新地址。
- 单密钥直接使用；多密钥首期选择一个启用密钥，返回的候选只代表该密钥视角，不暗中查询全部密钥或取权限并集。无可用密钥时明确报错。

对于截图这种地址、类型不变且密钥留空的编辑场景，可以通过后端直接使用已存凭证完成查询，无需先显示或复制真实密钥。

成功响应沿用本站现有 envelope：

```json
{
  "success": true,
  "data": ["model-a", "model-b"]
}
```

接口由 `AdminAuth` 及现有管理请求保护链处理，前端复用 `apiRequest()` 的同源会话与账号归属头。可使用现有审计中间件记录操作元数据；审计不记录请求体和密钥，业务配置数据保持不变。

### 5. 上游请求、地址与返回值处理

首期聚焦截图中的 OpenAI 类型（`type: 1`）和自定义 OpenAI 兼容上游。此次实际请求目标应为：

```text
GET http://103.186.215.40:3000/v1/models
Authorization: Bearer <selected key>
Accept: application/json
```

上述仅为请求结构说明，本轮没有发送该请求，也没有证明该上游实现了此端点。

当前渠道地址约定是主机及端口，不包含末尾 `/v1`。获取接口应与聊天请求遵循同一约定，并修正表单中含 `/v1` 的占位提示。可以在发现前对末尾 `/v1` 给出纠正提示；如果选择自动兼容这类输入，应同步统一聊天、Responses 和其他接口的 URL 处理，避免“获取成功、聊天仍然重复 /v1”。不要只为获取功能临时采用另一套不一致规则。

后端新增轻量服务负责组装请求和解析以下标准结构：

```json
{
  "object": "list",
  "data": [
    { "id": "model-a", "object": "model" },
    { "id": "model-b", "object": "model" }
  ]
}
```

仅取 `data[].id`，去除空白、空项及重复项，保留大小写和原始模型标识，不擅自改成平台别名。ID 必须适合当前逗号分隔存储及后续校验，不能把带分隔符、控制字符或超限标识悄悄转成不同模型。无效结构应报错；合法 `data: []` 返回空列表提示，且不清空原输入。

模型列表请求应有请求上下文、连接及总超时、响应体和条目数量上限；超限应明确提示，不静默截断。对供应商分页响应需明确支持范围，不能把未翻页的一部分当作完整清单。禁止将认证头自动跟随重定向带往另一服务；地址限制需与网关允许的上游部署范围一致，并拒绝无效协议、URL 内嵌凭证等输入。

错误应区分上游 401/403、404、429、超时、网络失败及响应格式错误，保留重试入口和原表单。上游拒绝认证应显示为获取错误，不把它冒充本站会话过期而触发全局登出。返回受控的错误文本，避免透传上游响应体或包含凭证的异常。

这个功能只读取模型目录，不应复用会发送聊天、变更渠道状态的 `TestChannel` / `ApplyProbeResult` 流程。目录获取成功也不代表所有模型都能推理、支持所有端点或已经具备平台计价。

Claude、Gemini、AWS Bedrock 与视频任务插件的目录、认证和返回格式不同。首期未适配的类型应隐藏或禁用该按钮并说明原因，保留手工录入；后续再按实际提供方实现，不统一调用 `/v1/models`。

### 6. 请求生命周期与已有配置保护

前端发现状态应绑定当前账号、弹窗会话、渠道 ID、类型、地址和密钥草稿；密钥只保留在当前内存中，不能进入可持久化查询键。请求带递增序号及 `AbortController`，旧请求即使晚返回也不能覆盖新状态。

关闭弹窗、切换账号或渠道、修改地址/类型/密钥时，取消或作废旧结果，并显示“连接配置已变化，请重新获取”。同一请求期间禁用再次获取；获取未完成时如允许保存，应在保存开始时使旧发现请求失效，防止保存后突然改动表单。若后台复用的凭证在其他会话已更新，应以查询时读取的凭证为准；后续渠道保存仍走原有写入逻辑。

已获取模型只是候选。普通渠道保存新增模型后可能扩大实际路由候选，因此不能默认把全量上游模型直接写库；托管渠道保存模型字段也不能绕过显式发布的准确模型/分组授权。

## 十二、渠道资源启用三态的口径修复（2026-11-19）

### 1. 问题与原因

已查看 `cc1.png` 红框。当前渠道状态组件已有“启用、部分启用、关闭”三态，但 `web/src/lib/channel-status.ts` 按 `key_count`、`multi_key_status` 统计 API Key，单 Key 渠道即使配置多个模型也只有全开/全关。按钮调用 `PUT /api/channel/{id}/status`，后端只修改渠道总开关，启用时还清空密钥禁用状态，因此没有真正的逐资源启停记录。“部分启用”分支及原 11 项测试覆盖的是多 Key 场景，未验证单 Key、多模型资源的需求。原有 `status=3` 表示自动禁用，不能改作部分启用。

本轮明确按渠道模型 ID 统计资源：普通渠道取其配置的模型并去重；托管渠道取当前已发布路由的模型 ID，并按模型去重，同模型投放多个分组不重复计数。托管渠道的公开模型别名是实际调用和开关对象，不按上游名称猜测绑定。资源总数大于零且全部启用为“启用”，零启用或渠道关闭为“关闭”，其余为“部分启用”，并显示启用数/总数。它描述运行开关，不代表上游健康检查成功，也不替代发布或分组授权。

需要独立、持久化的模型资源停用记录，与密钥健康、资源映射和投放授权分开。复用投放 `placement.enabled` 会触发 `invalidateResourceGatewaySources()`，导致整条托管发布撤销，不适合即时关闭单资源。新记录以渠道 ID 和实际模型 ID 为键，默认没有停用记录即启用，兼容现有渠道；同一资源的所有分组共享运行开关。修改必须在渠道配置事务中完成，验证资源属于该渠道；普通编辑、探测和重建能力不能恢复被停用的资源，未知或已撤销发布的资源也不能靠“启用”重新获得授权。渠道全部启用恢复其现有资源开关及渠道总开关，保留原密钥禁用状态；单项操作在渠道总开关关闭时不暗中开启其他资源。
