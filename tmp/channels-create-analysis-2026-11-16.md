# 渠道管理新增入口与自定义渠道接入分析

日期：2026-11-16。

分析依据：`cc1.png` 与当前工作区源码。本次仅新增本文档，未修改业务代码、创建渠道、写入数据库或请求上游服务。真实密钥不记录在本文档中。

## 一、当前页面为什么没有新增渠道按钮

`/console/channels` 通过 `web/src/features/channels.tsx` 加载 `ResourceInventory`，实际展示“渠道资源与投放”。

该页面负责导入资源快照、维护资源实例的模型映射与分组投放，以及预览和发布网关绑定。顶部现有操作为刷新、导入快照、网关发布预览和区域目录，没有接入真实渠道创建表单。截图与当前源码一致。

页面提示区已有“打开后台渠道”链接，目标为 `/admin?tab=resources`。该后台资源页已提供真实渠道列表、“新建渠道”、编辑、删除和测试连通能力。缺少新增按钮属于当前页面的功能入口未整合，不代表系统尚未实现渠道创建。

主要证据：

- `web/src/features/channels.tsx`：渠道页面入口。
- `web/src/features/resource-inventory.tsx`：顶部操作、后台渠道链接、资源列表和发布区域。
- `web/src/pages/admin/index.tsx`：真实渠道列表及创建、编辑弹窗。
- `web/src/main.tsx`：`/admin/*` 路由仍存在，并受登录及管理员权限限制。

历史 `web/HANDOFF.md` 中“无独立后台、无真实网关”等描述属于旧演示阶段，与当前代码不一致；本分析以当前路由、控制器和数据模型为准。

## 二、是否可以在当前页增加功能

可以，基础创建能力已经存在：

| 层级 | 现有实现 | 可复用内容 |
| --- | --- | --- |
| 前端表单 | `web/src/pages/admin/index.tsx` | 类型、名称、密钥、模型、分组及上游地址 |
| 前端接口 | `web/src/lib/api/channel.ts` | `useCreateChannel()`、编辑和删除 hooks，以及相关查询缓存失效 |
| 后端路由 | `internal/router/router.go` | `POST /api/channel`，管理员鉴权及审计 |
| 创建控制器 | `controller/channel.go` | 类型、模型、分组、地址和状态等处理 |
| 数据模型 | `model/channel.go` | 事务内保存渠道并重建路由能力 |

现有类型包括 OpenAI、Claude、AWS Bedrock、Gemini 和视频任务插件。普通的 OpenAI 兼容供应商可通过 OpenAI 类型配合自定义上游地址接入，无需新增供应商类型。

仅把真实渠道创建能力接入当前页面，通常不需要新增数据库表或后端创建接口。

## 三、真实渠道与资源快照的边界

| 对象 | 主要内容 | 创建真实渠道后的变化 |
| --- | --- | --- |
| 真实渠道 | 上游凭证、地址、类型、模型、分组及状态 | 新增一条渠道记录，按配置生成普通渠道路由能力 |
| 资源快照 | 来源渠道、资源实例、能力、区域及投放清单 | 不会因真实渠道创建而自动生成 |
| 发布绑定 | 来源渠道与真实渠道的显式关联及准确模型/分组组合 | 需要资源清单、投放配置及明确预览发布 |

因此，新增真实渠道后，截图里的“0 个资源”仍可能保持不变；新渠道可出现在网关发布上下文的真实渠道候选列表中。不能用资源数不变判断渠道创建失败。

普通渠道直接使用配置的模型和分组；托管渠道使用资源页明确发布的准确组合。普通渠道接入不要求先导入资源快照。

需要特别区分创建与发布：现有后台表单默认 `status: 1`，创建后会生成启用的普通渠道路由能力，可能进入实际调用候选；不能把所有渠道创建都描述为“等待资源发布”。

证据：`model/ability.go`、`model/resource_catalog.go`、`model/resource_publication.go`、`web/src/features/channel-routing-notice.tsx`。

## 四、建议的页面改造范围

1. 在 `/console/channels` 顶部增加固定的“新增渠道”主按钮，抽取并复用现有创建表单。
2. 增加真实渠道列表或页签，提供编辑、启停及测试入口，让创建成功后有明确落点。
3. 保留资源快照、模型映射、投放与发布流程，并显示真实渠道的关联状态。
4. 明确提供启用状态选择；如果产品流程要求先测试再上线，可默认禁用并由管理员主动启用。
5. 补齐接口失败提示、提交中保护和成功后的查询刷新。当前创建弹窗没有明确展示创建失败结果，不能只移动现有代码而忽略反馈。
6. 创建入口不应依赖已有资源快照；没有快照时也应能创建普通渠道。

第一阶段建议完成“当前页新增真实渠道 + 渠道列表”的操作闭环。自动生成来源渠道、资源实例、绑定与投放属于进一步整合，需要额外处理资源必填字段、版本冲突及明确发布规则。

现有表单虽然初始化了 `status`、`priority`、`weight` 和 `key_mode` 等字段，但没有对应的完整编辑控件。建议增加状态选择是后续改造建议，并非当前页面已有能力。

## 五、本次自定义渠道应如何填写

用户提供的服务地址为 `http://103.186.215.40:3000/v1`。以下方案以该服务支持 OpenAI 兼容聊天接口及 Bearer 密钥认证为前提；未访问服务，兼容性和密钥有效性尚未验证。

### 1. 地址必须去掉末尾 `/v1`

当前 OpenAI 适配器的聊天 URL 构造方式是：

```text
trimBase(base_url) + "/v1/chat/completions"
```

`trimBase()` 只清除空白和末尾斜杠，不会清除 `/v1`。因此：

| 渠道中填写的 base_url | 当前代码生成的聊天请求地址 |
| --- | --- |
| `http://103.186.215.40:3000` | `http://103.186.215.40:3000/v1/chat/completions` |
| `http://103.186.215.40:3000/v1` | `http://103.186.215.40:3000/v1/v1/chat/completions` |

本次应填写 `http://103.186.215.40:3000`。

现有表单的上游地址占位提示为 `https://api.openai.com/v1`，与聊天适配器实际拼接规则不一致，后续应修正提示，或统一适配器的路径规范化。Responses 地址有单独处理逻辑，不能据此推断聊天、图片及其他接口都接受含 `/v1` 的地址。

证据：`relay/channel/openai/openai.go` 中的 `ChatURL()`、`ModeURL()`、`trimBase()`，以及 `web/src/pages/admin/index.tsx` 的 `ch-base-url` 输入框。

### 2. 现有界面的操作路径

使用已完成管理安全设置的管理员或 Root 账号：

1. 在当前页面点击“打开后台渠道”，或打开本站 `/admin?tab=resources`。
2. 在“渠道列表”右侧点击“新建渠道”。
3. 按下表填写并创建。
4. 在新渠道所在行点击“测试连通”，查看所选模型是否返回成功。

| 表单字段 | 本次建议值或填写方法 |
| --- | --- |
| 渠道类型 | `OpenAI`，对应 `type: 1` |
| 名称 | 例如 `Custom-103.186.215.40`，可自行命名 |
| 密钥 | 在密码输入框中填入用户提供的完整密钥，不附加 `Bearer ` 前缀 |
| 模型 | 填入该上游和该密钥实际可用的准确模型 ID；多个模型使用英文逗号分隔 |
| 分组 | 可使用 `default`，或平台实际配置的目标分组；需与后续调用令牌的分组匹配 |
| 上游地址 | `http://103.186.215.40:3000` |

认证适配器会自行构造 `Authorization: Bearer <key>`，无需用户把认证前缀放进密钥字段。

当前界面默认创建为启用状态，并未提供创建时的状态选择。若希望先禁用创建再测试，可使用已有管理 API 的 `status: 2`；测试成功后再通过更新 API 显式设为 `status: 1`。手动禁用渠道不会因为测试成功自动启用。

### 3. 当前还缺少模型信息

后端要求 `models` 为非空的英文逗号分隔列表。只有 URL 和密钥仍不足以确定可用配置，不能任意填入一个常见模型名。

模型 ID 可以从供应商控制台或文档确认；若供应商实现标准模型列表接口，也可以使用该密钥查询 `GET http://103.186.215.40:3000/v1/models`。该接口是否存在及返回哪些模型，本次未验证，当前新建表单也没有自动拉取上游模型的操作。

下面仅为禁用创建的请求结构示例，不可直接把占位值作为有效渠道配置提交：

```json
{
  "name": "Custom-103.186.215.40",
  "type": 1,
  "key": "<enter the provided key securely>",
  "base_url": "http://103.186.215.40:3000",
  "models": "<actual upstream model ID>",
  "group": "default",
  "status": 2,
  "priority": 0,
  "weight": 1
}
```

请求目标为本站 `POST /api/channel`，使用本站管理员会话。上游密钥只用于渠道凭证，不是本站管理员会话凭证。

### 4. 测试与正式调用的区别

后台“测试连通”会向上游发送一次真实的最小聊天请求，内容为 `ping`，`max_tokens` 为 1，可能产生上游用量；未指定模型时使用渠道配置中的第一个模型。它不能证明所有配置模型或全部接口能力均可用。

正式从 StarHub 调用，还需核对平台调用令牌的分组与模型权限、余额，以及目标模型的计价配置。接入托管资源投放时，还需导入或维护相应资源清单，并显式绑定、预览和发布。

给定上游地址使用 HTTP，实际发送的凭证和请求内容不受 TLS 加密保护；供应商若提供 HTTPS 地址，应优先使用。

## 六、本轮结论与验证边界

现有代码支持通过 OpenAI 类型接入自定义地址，不需要为该 IP 专门开发一种渠道类型。本次地址应填主机及端口，去掉末尾 `/v1`；创建前还需确认准确模型 ID 和实际协议兼容性。

本轮完成截图及源码分析和文档保存，没有执行构建或测试，没有创建真实渠道或验证服务连通性，也没有使用或保存真实密钥。
