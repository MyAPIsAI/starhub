## 1. 问题与已核实原因

### 1.1 插件版本无法选择

- 下拉框的数据来自 `GET /api/task-plugin`，只展示数据库中已上传的插件版本；版本指 JavaScript 协议适配插件的版本，不是供应商模型版本。
- 上一轮只读检查时，本地 `starhub.db` 和 `starhub-dev.db` 的 `task_plugins` 表均为空。这与截图中只有“选择版本”占位项的现象一致；该结论不代表已核实运行进程的所有环境变量或其他数据库。
- 仓库有插件脚本，不等于脚本已经上传并注册到数据库。
- 当前表单缺少加载中、空列表引导及刷新版本入口；接口失败时只有错误文字，没有就地重试按钮。
- 当前禁用版本仍然可以在下拉框中被选中。新渠道应限制选择已启用版本；编辑已有渠道时应保留原禁用版本的显示，避免误改历史绑定。

### 1.2 视频插件类型不显示“获取上游模型”按钮

- `ChannelModelDiscovery` 仅在 `connection.type === 1`，即 OpenAI 类型时显示获取按钮。
- 后端 `FetchChannelModels` 同样只接受 OpenAI 类型，并按当前配置请求上游 `/v1/models`。
- 视频任务插件的渠道类型是 `61`，因此当前没有该按钮是能力限制；单独放开前端显示仍会被后端拒绝。
- 插件通过 `meta.models` 声明支持的模型。保存渠道时，后端要求渠道模型属于该声明集合；任务提交时也会再次检查。
- 当前插件契约只有元数据及提交、查询相关转换，没有模型发现 hook。

## 2. 上一轮建议

### 2.1 补齐版本选择流程

1. 明确区分加载中、加载失败、没有插件、只有禁用版本、有可用版本。
2. 空列表提示“请先上传视频任务插件”，增加“管理插件”和“刷新版本”按钮。
3. 管理入口在新标签页打开 `/admin?tab=plugins`，保留当前新建渠道弹窗的输入；不要把密钥写入 URL 或持久化草稿。
4. 上传后返回原弹窗并刷新版本列表，不自动替换用户已选择的版本。
5. 新建渠道只能选择已启用版本；编辑时保留原绑定的禁用版本显示，并说明禁用状态不接收新任务。

### 2.2 先增加“从插件选择模型”

1. 选择版本后解析该版本的 `meta_json`，展示 `models` 候选集合。
2. 按需勾选并填入渠道模型；不默认把全部模型加入渠道。
3. 切换插件时检查现有模型，明确提示不兼容项，不悄悄覆盖手工输入。
4. 标注数据来源为“插件声明”，不把本地声明标成“已从上游获取”。

### 2.3 实时上游模型获取应作为单独能力

如果需要实时获取供应商账户可见模型，需要按供应商协议扩展模型发现能力，不能假定所有视频供应商都提供 OpenAI `/v1/models`。

取得上游模型后，还需与所选插件声明的模型取交集；获取成功只说明目录可读取，不等于视频生成、查询或计费已通过真实厂商联调。

### 2.4 截图中的 doubao 渠道

仓库示例 [openai-video.js](../plugins/tasks/openai-video.js) 的版本为 `1.1.0`，只声明 `sora-2`、`sora-2-pro`，提交路径为 `/v1/videos`。渠道名称 `doubao` 不会改变适配协议；接实际豆包视频上游需要核实并导入匹配的插件。

### 3.1 new-api 实际如何提供插件和模型

| 环节 | new-api 本地实现 | 对 StarHub 的启示 |
| --- | --- | --- |
| 内置插件 | `plugins/embed.go` 嵌入 `tasks` 并注册 factory 插件 | new-api 的默认候选不仅来自数据库；不能因其有默认豆包选项，就认为 StarHub 的版本列表也应自动存在 |
| 可绑定插件 | `GetTaskPluginOptions` 从 registry 的 override/factory 层整理可用插件，返回名称、模型等信息 | 渠道编辑需要可用候选和明确状态；不需要先做插件市场 |
| 选择插件 | 渠道编辑器的 `selectProvider` 写入 `task_plugin_key`，并将 `plugin.models` 填入模型表单 | 插件声明已足以形成模型候选；StarHub 可复用此思路，但由用户勾选确认实际加入的模型 |
| 通用获取按钮 | 前端 `MODEL_FETCHABLE_TYPES` 不包含类型 61 | new-api 并未要求每个视频插件都有通用实时上游模型获取按钮 |
| 后端插件模型分支 | `fetchChannelUpstreamModelIDs` 对类型 61 直接返回 registry 中的 `plugin.Meta.Models` | 此分支读取本地声明，不访问供应商模型目录；应准确标注来源 |
| 厂商视频 | 豆包插件声明专属路径、转换请求和任务结果 | 需要厂商适配脚本，不能只改渠道名称或模型列表 |

证据入口：

- [内置插件注册](../../new-api/plugins/embed.go)：`init`、`RegisterFactory`。
- [可绑定插件选项](../../new-api/controller/task_plugin.go)：`GetTaskPluginOptions`。
- [渠道编辑器](../../new-api/web/src/features/channels/components/drawers/channel-mutate-drawer.tsx)：`taskPluginOptionsQuery`、`selectProvider`、`handleFetchModels`。
- [可获取模型的类型集合](../../new-api/web/src/features/channels/constants.ts)：`MODEL_FETCHABLE_TYPES`。
- [后端模型目录分支](../../new-api/controller/channel_upstream_update.go)：`fetchChannelUpstreamModelIDs`。
- [插件模型选配界面](../../new-api/web/src/features/channels/components/channel-plugin-extensions.tsx)：模型候选和已选数量。

注意：后端公共函数存在类型 61 分支，不等于新建渠道预览接口已支持传入插件绑定。该仓库的 `fetchModelsRequest` 与前端预览请求没有 StarHub 式的 `task_plugin_id`；不能直接移植一个分支后就认为草稿查询已完整支持插件。

### 3.2 两个项目不能直接互换插件

| 项目 | StarHub 当前契约 | new-api 当前契约 |
| --- | --- | --- |
| 执行环境 | goja，脚本包在同步函数中执行 | 独立的 jsplugin 注册与运行系统 |
| 导出方式 | `var meta` 和全局函数 | `export const meta`、导出的 hooks |
| 渠道绑定 | 固定 `task_plugin_id`，任务也记录该版本 ID | 渠道通过 `task_plugin_key` 选择运行时插件，另有版本管理及 factory/override 层 |
| 提交转换 | `prepareSubmit(ctx)` 返回相对路径请求及用量 | `buildSubmitRequest(ctx)` 返回含 URL 的描述，另有独立的请求解码与用量 hooks |
| 提交响应 | `parseSubmit(ctx, response)` | `parseSubmitResponse(ctx, response)` |
| 任务查询 | `buildQuery`、`parseQuery` | `buildQueryRequest`、`parseTaskResult`，另有批量查询等能力 |
| 结果 | 小写状态、数字进度、`outputs` 数组 | 例如 `SUCCESS`、字符串进度、`url`，宿主再生成协议输出 |
| 支持范围 | 统一视频 JSON 入口、固定的提交查询生命周期 | 厂商原生路由、Responses、OpenAI 视频/图片、多种请求体及其他扩展 |

两边都出现 `apiVersion: 1` 只是各自契约的版本号，不能据此判断兼容。直接上传 new-api 的 `export` 脚本，StarHub 当前编译包装及必需函数检查无法接受。

## 4. 建议优先实现：版本闭环与插件模型选择

### 4.1 数据流

```text
GET /api/task-plugin
  → 显示已上传版本及启停状态
  → 管理员明确选择 task_plugin_id
  → 解析该版本的 meta_json.models
  → 搜索、勾选、添加模型到表单
  → 显示不兼容项和提交错误
  → 用户明确保存渠道
  → 后端重新校验版本、单密钥、地址和模型归属
```

这一阶段无需新建模型发现接口，无需修改插件运行时或数据库结构。OpenAI 渠道继续通过现有接口访问上游目录。

### 4.2 版本字段与管理入口

- 加载中：版本下拉框显示加载提示并禁用，防止把未完成查询误认为没有插件。
- 加载失败：显示明确错误及重试按钮，不降级为无提示的空列表。
- 没有版本：提示“尚未上传视频任务插件”，提供新标签页的“管理插件”和就地“刷新版本”。
- 只有禁用版本：提示“暂无已启用版本”，引导到管理页启用或上传；不把禁用版本当成可用候选。
- 有启用版本：展示 `key + version`，保留版本 ID 作为表单值；刷新列表不能自动升级已有选择。
- 编辑原禁用版本：保留该绑定的显示并提示“不接收新任务”；允许用户保留原绑定编辑其他配置，或主动换绑启用版本。
- 已选择的版本若刷新后丢失或被禁用，应立即更新提示和新建/换绑提交状态，不能沿用旧的可用判断。

不要通过 `localStorage`、URL 或其他持久化方式保存密钥来维持页面草稿。新标签页管理加显式刷新，已经可以保留原弹窗的 React 内存状态。现有应用配置了 `refetchOnWindowFocus: false`，不能只依赖切回页面触发重新请求。

### 4.3 复用模型选择组件

建议兼容扩展现有 `ChannelModelDiscovery`，复用搜索、勾选、选择搜索结果和“添加所选模型”交互，不另建一套几乎相同的选择弹窗。

组件根据数据来源明确分支：

- `type === 1`：保持“获取上游模型”，调用现有 `POST /api/channel/fetch_models`。
- `type === 61` 且未选择插件：显示“请先选择插件版本”。
- `type === 61` 且插件有效：提供“从插件选择模型”，读取该固定版本的声明；不发送上游请求，不需要填写 Key 或 Base URL 后才能查看本地候选。
- 其他类型：保留现有手工输入方式，不借本次修复扩大其发现能力。

`TaskPluginVersion` 可继续使用现有响应；新增前端元数据类型和受控解析即可。解析需要检查 JSON 对象、`models` 字符串数组及合法模型标识，失败时显示“插件元数据不可用”，不能把格式错误当作成功取得零个模型。

模型选择结果应明确标注“插件声明 · 未验证上游账户可用性”。候选列表不等于渠道授权列表；只有用户点击“添加所选模型”并保存后才生效。

当前组件将结果区称为“上游模型选择”，并把未返回的现有模型视为可以保留。复用时必须一并调整来源文案和校验语义：OpenAI 目录未列出某模型可以保留手工输入；插件未声明的模型却无法通过后端校验，应标为不兼容项。

### 4.4 切换版本与异步结果

1. 切换插件版本后清空候选勾选和旧提示，改用新版本模型集合。
2. 保留模型输入框原值，但展示不兼容项并阻止错误提交；用户可明确移除这些项，再添加新候选。不要无提示删除手工输入，也不要自动扩充为插件全部模型。
3. 扩展现有请求签名或结果标识，将登录身份、渠道类型、插件版本 ID、有效元数据纳入一致性检查，避免旧版本候选在切换后仍可被添加。
4. 页面切换身份或退出时，不继承上一个身份的插件候选和临时结果。

### 4.5 后端校验补齐

仅改前端不能防止绕过页面的新建/换绑。建议在已有渠道保存事务内补充：

- 新建插件渠道或改变 `task_plugin_id` 时，目标版本必须存在且已启用。
- 编辑时如果原版本 ID 未改变，保留原禁用版本的配置，不强迫迁移历史渠道。
- 继续执行当前单密钥、Base URL 和 `channel.models ⊆ plugin.meta.models` 校验。
- 继续保留旧任务自己的版本 ID。插件被禁用后，已有任务仍走原轮询逻辑，不因表单候选筛选而中断。
- 渠道创建和编辑失败时，在弹窗内显示后端错误；当前表单只在成功回调关闭窗口，缺少完整的失败反馈。

这是小范围的保存约束补齐，不需要改造任务生命周期或版本存储。

## 5. 若实际需要豆包视频：移植协议适配，不直接复制脚本

### 5.1 可参考的内容

本地 new-api 的 [doubao/plugin.js](../../new-api/plugins/tasks/doubao/plugin.js) 声明版本为 `1.4.0`，包含 Seedance 视频和 Seedream 图片；本次目标为视频时，只提取视频所需的协议转换思路。

从该代码核实的路径与形状：

- 提交：`POST /api/v3/contents/generations/tasks`。
- 查询：`GET /api/v3/contents/generations/tasks/{taskId}`。
- 文生视频请求把文本放入 `content` 的 `text` 项，时长映射为 `duration`。
- 成功结果使用 `content.video_url`。
- 代码区分 `queued`、`running`、`succeeded`、失败类及未知状态。

这些是参考代码采用的约定，不是本轮对真实豆包账户的联调结论。供应商可用模型、权限和参数范围仍应在正式接入时核实。

### 5.2 适配到 StarHub 四个 hooks

| StarHub hook | 可参考 new-api 的部分 | 必须按 StarHub 契约改写 |
| --- | --- | --- |
| `prepareSubmit` | `buildSubmitRequest` 中的视频请求构造 | 使用 `ctx.request`、相对 `path`，认证由宿主按 `meta.auth` 注入；不把 Key 放进脚本上下文 |
| `parseSubmit` | `parseSubmitResponse` 中的任务 ID 提取 | 返回 StarHub 的 `{taskId}`，处理缺失 ID 和上游业务错误 |
| `buildQuery` | `buildQueryRequest` | 使用 `/api/v3/contents/generations/tasks/` 加编码后的任务 ID，相对路径和 GET 描述 |
| `parseQuery` | `parseTaskResult` 中的状态及结果提取 | 映射为 StarHub 小写状态、数字进度及 `outputs` 数组；成功须有可用结果 URL |

开始时建议只承诺当前统一请求能表达的文生视频子集；图片输入、视频参考、原生厂商请求体和特殊自动时长等，须另行核对 DTO、校验、预估和上游契约后再扩展。

不能将 new-api 的 `duration = -1`、专属 usage profiles、图片/SSE 支持、原生路由或 `utils` 依赖直接带入 StarHub。当前请求要求正数 `seconds`，两边用量与结果形状也不同。未知状态应明确作为解析失败交由现有轮询错误处理，不伪装成已成功或永久进行中。

模型声明应使用已适配、经确认需要开放的实际模型 ID，不照搬参考仓库全部模型，也不把 Seedream 图片模型混入视频渠道。旧版和新版脚本保持不同版本号，继续使用已有不可变源码和任务版本快照。

### 5.3 费用与验收边界

模型选择修复不改变计费逻辑。若随后增加豆包适配，用量解析必须作为独立验收项：显式输入/输出 tokens、总 tokens 与时长不能互相冒充；上游字段不足时如何沿用预估，应沿用并核对当前 StarHub 规则，而非复制参考项目的计费 hooks。

本轮未编写、上传或执行豆包插件，也没有验证实际生成结果。上述适配方案不能描述为现成可用的豆包插件。

## 6. 两项可选扩展及其复杂度

### 6.1 内置插件安装入口

如果期望首次打开页面就能选择示例，可借鉴 new-api 的内置来源，但第一步只增加管理员主动安装的本地模板入口，仍将安装后的脚本保存为现有 `task_plugins` 版本记录。

这样可继续使用 `task_plugin_id` 和旧任务版本快照，无需引入完整的 factory/override 注册系统、插件市场或渠道按 key 自动跟随激活版本。自动启动时安装并启用插件会改变当前操作语义，不建议作为本次缺少提示的默认修复。

### 6.2 实时上游模型目录

若未来确认供应商提供合适的目录接口，再增加显式能力：

1. 定义模型目录路径、认证及响应转换，或受限的可选模型发现 hooks；由宿主发出只读请求。
2. 草稿请求必须携带所选固定版本 ID，并遵守已有草稿/已保存渠道凭证复用边界；仅改 `type` 判断不够。
3. 请求签名纳入插件版本，继续取消旧请求并丢弃过期结果；超时、失败和空交集分别提示。
4. 上游结果与插件支持集合取交集；不支持目录的插件继续使用本地声明，来源在界面中明确区分。
5. 不通过提交真实视频任务来“获取模型”或判定目录可用性；渠道测试当前也只是本地插件校验。

该扩展属于中等复杂度，会涉及运行时或接口契约。当前参考的 new-api 类型 61 分支只是返回本地声明，并不证明所有视频供应商都需要这项扩展。
