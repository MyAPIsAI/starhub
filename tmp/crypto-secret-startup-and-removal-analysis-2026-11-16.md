# go run 启动、STARHUB_CRYPTO_SECRET 用途与移除可行性分析

日期：2026-11-16。

本文先归档上一轮关于 `go run .` 启动配置的分析，再说明 `STARHUB_CRYPTO_SECRET` 的实际作用及是否可以取消。本次仅新增分析文档，未修改加密实现、启动代码或数据库，也未生成、替换或记录真实密钥。

## 一、上一轮启动分析归档

### 1. go run 命令可以继续使用

`go run .` 编译并启动当前 Go 后端，默认不嵌入前端。日志中的 `web console: not embedded` 与根路径 `/` 返回 404 是该开发模式的正常行为；前端使用 Vite 的 5173 端口访问。这不是凭证迁移失败的原因，换成发布程序也不能自动补回缺失的加密配置。

当前启动失败发生在数据库凭证迁移阶段，需解决的是加密配置的加载和持久化。当前 Go 程序从环境变量读取加密配置，不自动加载 `.env` 或 `web/.env.local`；`config.yml` 目前也没有加密密钥或密钥文件配置项。

### 2. 先恢复已有数据库所需的原配置

复用已有数据库时，应恢复创建凭证时使用的同一个 `STARHUB_CRYPTO_SECRET`。如果之前启用了版本密钥环，还需恢复对应的 `STARHUB_CREDENTIAL_KEYS` 及 `STARHUB_CREDENTIAL_ACTIVE_KEY`。

若能找回原值，可在准备执行 Go 的同一个 PowerShell 中通过隐藏输入加载：

```powershell
$secret = Read-Host "Original STARHUB_CRYPTO_SECRET" -AsSecureString
$env:STARHUB_CRYPTO_SECRET = [System.Net.NetworkCredential]::new('', $secret).Password
Remove-Variable secret

go run .
```

上述变量只对当前 PowerShell 及之后启动的子进程生效，不会替用户长期保存密钥。密钥应从原有受保护的配置来源恢复，不能任意生成新值去解密旧数据。

此前只读核验发现，当前工作区数据库有 1 条渠道凭证与 1 条客户令牌，均采用 `enc:v2` 格式、`legacy` 包装密钥标识。标识只说明该记录使用哪个版本，不包含密钥本身，也不能证明原密钥此前是人工配置还是随机生成。

如果此前未设置持久密钥，当前实现会在每个新进程中生成随机密钥；旧进程退出且密钥未保存后，新进程无法解密旧凭证。无论保留还是移除加密功能，都不能从旧密文凭空恢复已丢失的明文。

### 3. 避免之后重启重复出错的建议

如果希望今后每次只执行 `go run .`，建议增加开发环境的本地持久密钥加载：环境变量优先；未配置时读取受保护的本地密钥文件；只有确认是全新安装且没有依赖旧密钥的数据时，才允许生成并保存新密钥。已有加密数据却缺少原密钥时，应明确停止，不能静默生成新密钥冒充恢复成功。

| 修改位置 | 建议行为 |
| --- | --- |
| `main.go` 与启动配置模块 | 在首次调用加密配置验证或使用加密功能前，完成密钥加载 |
| 加密配置逻辑 | 支持稳定密钥来源，避免持久数据库使用进程随机密钥 |
| 首次初始化流程 | 区分全新安装、已有明文数据与已有加密数据，防止覆盖原密钥文件 |
| `.gitignore` 及文件权限 | 忽略本地密钥文件，限制其他用户读取，按数据库及密钥分别备份 |
| `cmd/credential-keys` 等运维入口 | 与主程序使用一致的密钥加载规则 |
| 测试 | 验证跨进程重启、环境变量优先级、旧格式兼容、缺失密钥和原文件不被覆盖 |

生产环境继续要求明确提供受管理的持久密钥，不使用临时随机回退。该方案是建议，尚未实现。

## 二、STARHUB_CRYPTO_SECRET 到底是什么

它是 StarHub 自己使用的服务端秘密配置，主要用于数据库凭证保护和客户 API 令牌查询。它不是供应商提供的上游 `sk-…` 密钥，也不是用户的登录密码。它不负责前端构建或决定使用 `go run .` 还是发布程序。

`common/crypto_secret.go` 的 `getEncryptionKey()` 会把该变量转换成 32 字节密钥：如果是可以解码为 32 字节的十六进制字符串，则直接使用解码结果；否则使用该字符串的 SHA-256。没有该变量时，目前生成进程内随机密钥。

### 1. 保护渠道的上游凭证

渠道需要真实密钥才能向供应商发送请求，因此上游凭证必须能够在运行时取回原文，不能简单用单向摘要代替。

当前 `model/channel_credential.go` 在写入数据库时调用 `EncryptCredential(..., "upstream")`；读取渠道时解密，供后台请求供应商使用。数据库中保存密文，不直接保存可用的上游密钥。

新版 `enc:v2` 为每个凭证生成一个随机数据密钥，用 AES-256-GCM 加密凭证，再用包装密钥保护数据密钥。没有配置独立密钥环时，`STARHUB_CRYPTO_SECRET` 派生的密钥作为 `legacy` 包装版本使用。

### 2. 保护可再次查看的客户 API 令牌

`model/token.go` 创建客户令牌时保存加密后的令牌，以及用于检索的 `key_hash`。查看或复制已存在令牌等需要原文的路径，会执行解密；相关控制仍需通过原有的身份和密码验证。

因此，保留“以后还能查看或复制同一个令牌原文”的产品行为，就需要可逆存储或另一种可取回凭证的外部系统。

### 3. 生成客户令牌查询摘要

`common/crypto_secret.go` 的 `HashKey()` 使用该秘密派生的密钥执行 HMAC-SHA256。客户端携带 API 令牌访问时，`GetTokenByKey()` 先计算摘要，再通过数据库 `key_hash` 查找令牌。

这个摘要不能反推出原始令牌。秘密改变后，同一原始令牌产生的摘要也会改变，已有查询索引就不再匹配。因此，即使通过独立版本密钥环保持了凭证解密能力，也不能随意变更或取消用于查询的 `STARHUB_CRYPTO_SECRET`。

启动迁移还会校验客户令牌的已有摘要是否与当前秘密一致；只忽略解密错误或移除日志提示，不会消除这种一致性要求。

### 4. 与其他安全机制的边界

该变量的直接用途是上述凭证加密、旧格式解密及相关摘要计算。账号密码使用自己的校验存储逻辑；登录会话、角色权限和接口鉴权也有独立实现。不能把“取消数据库凭证加密”误认为只是移除一个提示，也不能说它会自动取消全部登录和权限机制。

另外，`common/key.go` 中名为 `getCryptoSecret()` 的函数是另一份进程随机秘密，用于验证码 HMAC；它与环境变量 `STARHUB_CRYPTO_SECRET` 不是同一个密钥来源，分析或改造时应避免因命名相似而误改。

## 三、是否可以不要这个功能

需要区分“不再手动设置环境变量”和“不再保护数据库凭证”。技术上都可以调整，但所需改动与结果不同。

| 选择 | 是否可行 | 结果与约束 |
| --- | --- | --- |
| 不修改代码，直接不设置变量 | 当前不适合持久数据库 | 会使用新的进程随机密钥，重启后仍会出错；生产环境还会在启动校验中拒绝 |
| 保留功能，自动读取持久密钥文件 | 可行，适合简化本地开发 | 无需每次手动配置变量；仍需妥善保存文件，已有密文仍需原密钥 |
| 改用操作系统凭证库或外部密钥服务 | 可行 | 可减少手工管理环境变量，但仍有密钥、授权、备份与迁移依赖 |
| 只配置 `STARHUB_CREDENTIAL_KEYS`，取消原秘密 | 当前不能直接替代 | 该密钥环可接管新版凭证的包装，但客户令牌摘要与旧格式解密仍依赖原秘密 |
| 增加显式的开发明文存储模式 | 技术可行 | 需完整改造存储、查询和迁移；数据库及其备份将直接暴露可用凭证 |
| 客户令牌只存摘要，上游凭证交给外部秘密存储 | 技术可行，范围较大 | 可重新设计为不依赖这一特定环境变量，但需调整查看/复制功能、查询索引及上游凭证来源 |
| 在代码中写死通用密钥 | 不建议 | 拥有代码或程序的人可得到相同密钥，不应把它当作数据库凭证保护方案 |

### 1. 如果只是觉得启动麻烦

建议保留凭证加密，取消反复手工输入的操作：本地开发从受保护的持久密钥文件加载；发布程序和运维工具使用同一来源。文件应与对应数据库建立明确关联，避免换工作目录后读取另一份密钥。

这种方式不会让密钥失去作用。它主要保护数据库单独泄露或备份单独外流的场景；如果攻击者同时取得数据库和可用密钥，保护边界自然不同，因此不能宣称一个本地文件能够防止整台主机失陷。

### 2. 如果明确只做可丢弃的本地演示，要求完全取消凭证加密

技术上可以设计一个明确启用、仅限开发环境的模式，但它不是现有功能，不能靠删掉变量就实现。

至少需要处理：

1. 渠道字段序列化及 map 更新钩子：明确在该模式保存、读取明文，而不是继续调用加密函数。
2. 客户令牌存储：决定保存明文，还是只保存稳定摘要。若采用足够高熵的随机 API 令牌并仅保存 SHA-256 等摘要用于检索，可以不依赖查询 HMAC 秘密，但需要对应修改认证与数据迁移，并取消之后恢复原文的能力。
3. 查看、复制、重置令牌及密码验证相关逻辑：与选定存储方式保持一致。
4. 启动迁移：识别原密文、目标模式和查询摘要，迁移必须事务化，不能把 `enc:v2:...` 字符串直接当成上游密钥。
5. 配置校验和运维入口：明确生产环境是否禁止该模式，避免开发配置误用于实际运营。
6. 日志、响应、导出与备份：不能因为数据库改成明文就取消原来的脱敏和访问控制。
7. 测试：覆盖模式边界、令牌查询、原文展示行为、迁移回滚及凭证泄露防护。

上游凭证即使放弃数据库加密，也必须保留真正可用的密钥；将它改成单向摘要后，网关就无法用它调用供应商。若要避免在业务数据库保存可逆凭证，应改用外部秘密存储，并在请求时受控读取。

### 3. 如果原密钥已经丢失

取消功能也无法解密旧数据。需要区分以下恢复来源：

- 能找回原始服务端秘密：恢复配置，验证并保留现有凭证。
- 找不到服务端秘密，但知道某条上游原始密钥：可在明确恢复方案下重新配置该渠道凭证，不能据此恢复其他客户令牌。
- 客户仍持有原始 API 令牌：可能设计受控导入及索引重建流程，但不代表当前程序已有这样的恢复接口，也不能仅凭“持有令牌”就绕过账号归属校验。
- 没有原秘密，也没有相关原始凭证：保留备份后，只能按明确授权重设受影响的凭证。客户令牌重设会让旧令牌失效，需要更新客户端。

不需要为了修复少量凭证默认清空整个数据库。恢复操作应限定到相关记录，保留账号、余额、历史用量等其他数据，并检查所有引用关系；本轮没有执行任何重设或迁移。

## 四、对当前项目的建议

当前项目已经使用渠道管理、真实上游调用、客户 API 令牌和计费等能力，建议保留凭证保护，优先修复开发环境随机密钥不持久的问题，让 `go run .` 能稳定重复启动。

如果用户明确选择只用于本地演示、接受数据库明文凭证及产品行为变化，可以再实施显式开发模式；应先确定客户令牌采用明文还是仅摘要，以及现有两条加密凭证如何恢复。移除整个功能比增加持久密钥加载涉及更多模块和迁移边界。

以上推荐是基于当前代码及操作成本的工程判断，不是用户已经授权实施的改造。本次只写文档和分析，不修改功能、不读取真实密钥原文、不重设凭证或数据库。

## 五、源码依据与本轮验证边界

- `common/crypto_secret.go`：环境变量派生、随机回退、旧格式解密和客户令牌 HMAC 查询摘要。
- `common/credential_envelope.go`：版本密钥环、`legacy` 默认包装版本及 AES-GCM 信封格式。
- `model/channel_credential.go`：上游密钥的数据库字段读写加解密。
- `model/token.go`、`model/owned_token.go`：客户令牌创建、重置、加密存储与查询摘要。
- `controller/token_password.go`：受保护的令牌原文读取路径和凭证绑定摘要。
- `model/credential_migration.go`：启动时解密校验、摘要校验、事务迁移及失败回滚。
- `main.go`、`config/startup.go`、`config/production.go`：配置读取顺序、启动日志及生产校验。
- `CREDENTIAL_STORAGE.md`：凭证格式、原秘密保留及包装密钥轮换约定。

本轮通过本地源码核对完成分析，没有执行加密模式切换、数据库写入、真实上游请求或业务代码修改；文档中的新方案均未实施，因此未将既有测试结果冒充其验证结果。
